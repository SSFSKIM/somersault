# Agent app-server protocol — seam coverage scorecard

> Companion to [`docs/superpowers/specs/2026-07-28-agent-appserver-protocol-design.md`](../superpowers/specs/2026-07-28-agent-appserver-protocol-design.md)
> (spec §10, decision **D11**). That spec's "100% coverage" claim is only honest if its denominator
> is generated by walking the real source, not hand-counted — the "22 vs 25 host ops" miscount D11
> exists to prevent. `scripts/drift-check.mjs` gains an **appserver pass** that re-walks the same four
> sources on every run and fails when a walked token has no row here (extra rows — future/aspirational
> ones — are fine; a walked token with **no** row is not).
>
> **Scope of this scorecard:** the four sources spec §10 calls "generated, not hand-counted" —
> `host/ops.ts` (25 ops), `bridge/types.ts` (11 `ControlFrame` verbs), `sessions/index.ts` (7 store
> wrappers), and `sdk.d.ts`'s `interface Query` (27 methods) — **70 seam tokens** total. Spec §10's
> full denominator has two more legs (`docs/parity/tui-ux.md` §control-plane, the fleet CLI verbs);
> those aren't code-walkable the same way and stay tracked in `tui-ux.md` / `coverage.md`, not here.
>
> **Status legend:** `shipped(M1)` — live today in `harness/src/appserver/` for an **inProcess**-origin
> thread (verified by reading the actual handler code, not just the spec prose — see "M1 shipped, per
> the code" below). `planned(M2)` / `planned(M3)` — named in spec §7/§12 but not yet wired.
> `probe-gated` — spec explicitly says this needs a live probe before it can ship at all (D5 and the
> sessions-store note). `N/A` — no protocol method backs this token by design.
>
> **Origin-scope legend** (spec §2): `both` — reachable whether the thread is `inProcess` or adopted
> from a fleet host; `inProcess` — no corresponding host-wire op exists yet, so a fleet-origin thread
> gets `-33006 unsupportedForOrigin`; `fleet-only` — the mirror case (a handful of methods only make
> sense for an adopted host — not formally named in spec §2, which only defines the `inProcess`-only
> carve-out; see the discrepancy note below); `N/A` — no method, so no origin question applies.

## M1 shipped, per the code (not the spec prose)

Read directly from `harness/src/appserver/{server,turns,subscribe}.ts`: `initialize` (+`initialized`),
`server/status`, `thread/start`, `thread/resume`, `thread/list`, `thread/close`, `thread/subscribe`,
`thread/unsubscribe`, `thread/read`, `turn/start`, `turn/interrupt`, `decision/list`, `decision/respond`,
and notifications `thread/started`\*, `thread/status/changed`, `turn/started`, `turn/completed`,
`item/started`, `item/completed`, `item/agentMessage/delta`, `item/reasoning/delta`,
`item/toolCall/argumentsDelta`, `decision/requested`, `decision/resolved`. This matches the M1 list
handed into this task exactly, with one caveat: \*`thread/started` is not literally broadcast anywhere
in `server.ts`/`turns.ts`/`subscribe.ts` today — `thread/start`/`thread/resume` reply directly with the
thread view and never `ctx.peer.notify("thread/started", …)`. It is still listed as intended-M1 per the
brief; this file records the gap rather than silently agreeing it is wired.

`thread/list` in M1 is **registry-only** — it returns `srv.registry.list()`, i.e. live in-process
threads. The spec's fuller `thread/list` (merging session-store + fleet roster, dedup'd on `sessionId`)
is **not yet wired**: `listSessions`/`getSessionInfo` are not imported anywhere in `appserver/`. Rows
below reflect that: the *method* `thread/list` is `shipped(M1)`, but the *sessionWrapper* rows for
`listSessions`/`getSessionInfo` are `planned(M2)`.

## Notable gaps and discrepancies found while walking

1. **`turn/interrupt`'s `cancelQueued` is inert.** `turnInterrupt` (`appserver/turns.ts`) accepts
   `{cancelQueued?: boolean}` on the wire and silently ignores it — `record.session.interrupt()` is
   zero-arg. At SDK 0.3.220 `Query.interrupt(): Promise<SDKControlInterruptResponse | undefined>` is
   still zero-arg; `cancel_queued` exists only on the wire-level `SDKControlInterruptRequest`, behind no
   public method (spec's own *Surprises & Discoveries*, M1 T1). Every row this task backs to
   `turn/interrupt` carries this qualifier rather than a bare `shipped(M1)`.
2. **`host/ops.ts` and `bridge/types.ts` are not imported anywhere under `appserver/`.** `grep -rn
   "host/ops\|bridge/types\|bridge/control" harness/src/appserver` turns up nothing. M1's registry only
   supports `ThreadOrigin = "inProcess"` (`registry.ts:7`, `"fleet adoption is M3"`), so `thread/start`
   /`thread/resume`/`turn/start`/… reach the engine through `openSession`/`resumeSession`
   (`src/session/index.ts`) directly, never through the host wire or the bridge `ControlFrame` channel.
   Those two sources' tokens back the **same** protocol methods (spec §7 explicitly describes multiple
   backing seams per method), so this file scores each row by the method's *shipped status*, not by
   whether this particular token is literally referenced in `appserver/` yet — but the real wiring only
   exists for the in-process path today; the host-wire/bridge path activates when fleet adoption
   (`thread/attach`) lands in M3. Recorded here so "shipped(M1)" isn't misread as "this exact seam is
   called".
3. **`account/read` and `thread/init/read` have no backing host op.** Spec §2's explicit inProcess-only
   list is `thread/settings/apply`, `thread/reinitialize`, `mcpServer/set`,
   `mcpServer/permissionModeOverride/set`. Walking `host/ops.ts`'s 25 ops turns up none named
   `account`/`account_info` or `init`/`initialization_result` — so `account/read`
   (`Query.accountInfo`/`ControlFrame.account_info`) and `thread/init/read`
   (`Query.initializationResult`) are **also** inProcess-only today; spec §2's list is a documented
   omission, not a contradiction (growing the host wire to add these is exactly the "named follow-up
   work" §2 calls for). Scored `inProcess` here.
4. **`thread/stop`/`thread/attach` are the mirror of the inProcess-only rule.** They only make sense
   for a fleet-adopted thread (you `close`, not `stop`, an in-process engine). Spec §2 only names the
   `inProcess`-only direction; this scorecard adds `fleet-only` as the symmetric case rather than
   force-fitting `both`/`inProcess`.
5. **The existing SDK-drift pass's own `Query`-method extraction over-counts by 5** (`surfaces()`'s
   `block()` helper in this script looks for `"\n};"` to end a block, which is right for `type Options =
   {...};` but `interface Query {...}` closes with a bare `"\n}"` — no semicolon — so `block()` runs
   past the real end and picks up ~5 names from whatever the next semicolon-closed type happens to be:
   32 vs the true 27). It doesn't corrupt that pass's installed-vs-npm-HEAD *diff* (both sides share the
   identical over-read), so it's left untouched — out of scope for this task — but the new appserver
   pass below does **not** reuse `surfaces()`; it re-parses `interface Query` independently, terminating
   on the first flush-left `"\n}"` (verified: exactly 27 methods, matching spec §10's count).

## Totals

25 host ops + 11 ControlFrame verbs + 7 session wrappers + 27 Query methods = **70 walked tokens**,
all rowed above. `shipped(M1)`: 12 rows, collapsing (across duplicate seams) to 10 distinct protocol
methods — `thread/status/changed`, `decision/list`, `decision/respond`, `turn/start`, `turn/interrupt`,
`thread/subscribe`, `thread/unsubscribe`, `thread/resume`, `thread/read`, `thread/close`.
`probe-gated`: 4 (`readFile`, `reloadPlugins`, `reloadSkills`, `streamInput`). `N/A`: 1
(`seedReadState`). Remainder (53 rows): `planned(M2)`/`planned(M3)`.
