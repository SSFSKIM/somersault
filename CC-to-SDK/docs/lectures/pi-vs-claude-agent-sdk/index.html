Pi Agent Harness vs Claude Agent SDK
에이전트 프레임워크로서의 기능성과 커스터마이저빌리티

둘 다 "에이전트 프레임워크"라 불리지만 같은 종류의 물건이 아닙니다. Pi는 엔진을 소유하게 해주는 라이브러리이고, Agent SDK는 남의 엔진을 빌려 쓰게 해주는 원격 조종기입니다. 이 한 문장의 차이가 아래 모든 표의 원인입니다.

§0한 줄 결론

Pi를 고르면

"프레임워크가 내 워크플로에 맞춰야 한다"는 쪽. 커스터마이저빌리티는 사실상 천장이 없다.
  • 어떤 모델이든: 40개 프로바이더, 구독 OAuth 6종(Claude Pro/Max·ChatGPT·Copilot·xAI·OpenRouter·Radius)
  • 내장 툴 8개 중 무엇이든 같은 이름으로 등록하면 교체. 시스템 프롬프트는 통째로 교체 가능
  • TUI, RPC, JSON, SDK 네 가지 모드가 기본 제공. 세션은 트리(분기·포크)
  • 대가: 권한 시스템·MCP·서브에이전트·플랜모드가 없음. 직접 만들거나 패키지 설치. 에이전트 품질은 <1,000 토큰짜리 프롬프트 + 모델에 의존

Agent SDK를 고르면

"Claude Code 품질의 엔진을 그대로 빌리자"는 쪽. 기능 풍부함은 압도적이지만 엔진 안은 만질 수 없다.
  • 권한 6모드 + 룰 엔진 + 분류기, 서브에이전트, MCP 4종 전송, 스킬·플러그인, 샌드박스, 파일 체크포인트/되감기, 구조화 출력, 자동 컴팩션이 내장

§1아키텍처: 라이브러리 vs 서브프로세스

"확장할 수 있는가"는 결국 "그 코드가 어디서 실행되는가"의 문제입니다. Pi는 모든 것이 호출자의 프로세스 안에 있고, SDK는 의사결정 대부분이 자식 프로세스 안에서 일어납니다.

SDK 래퍼가 실제로 하는 일

query()는 옵션 객체를 CLI 플래그로 번역합니다. 기본 인자는 문자 그대로 ["--output-format","stream-json","--verbose","--input-format","stream-json"]이고, 여기에 --model, --permission-mode, --mcp-config, --setting-sources=, --resume=, --fork-session 등 약 40개 플래그가 붙습니다. canUseTool을 넘기면 --permission-prompt-tool stdio가 추가되어 권한 질문이 stdio로 돌아옵니다. 즉 SDK는 claude -p --output-format stream-json의 타입 있는 드라이버이며, 모델링되지 않은 플래그는 extraArgs로 강제 주입할 수 있습니다.

중요한 정정 하나: 흔히 "번들된 cli.js를 spawn한다"고 알려져 있지만, 0.2.113부터 네이티브 바이너리입니다. 설치본에는 cli.js도 bin 엔트리도 없고, executable: 'bun'|'deno'|'node' 옵션은 경로가 .js/.ts로 끝날 때만 의미가 있어 사실상 죽은 옵션입니다.

Pi 코딩 에이전트는 "멍청한 코어 위의 호스트"

sdk.ts:306-372가 배선도입니다. Agent는 systemPrompt: ""로 생성되고, 확장 이벤트가 코어 훅에 1:1로 묶입니다: context→transformContext, before_provider_headers→transformHeaders, before_provider_request→onPayload, tool_call→agent.beforeToolCall, tool_result→agent.afterToolCall. 코어(pi-agent-core)는 시스템 프롬프트 기본값이 빈 문자열이고 harness/system-prompt.ts는 34줄짜리 스킬 XML 포매터 하나뿐입니다. "코딩 에이전트다움"은 전부 coding-agent 층이 얹는 것이라, 같은 코어 위에 전혀 다른 에이전트를 올릴 수 있습니다.

Pi 쪽 유보 사항
packages/agent/src/harness/에는 2,941줄 스펙(docs/harness.md)을 가진 2세대 내구성 하네스(AgentHarness, 레인/레코드 세션 스토어 v4)가 있지만, 구현은 거의 전부 HarnessNotImplemented를 던집니다(harness/agent-harness.ts:347-442). 이 문서의 Pi 평가는 출하 중인 Agent 클래스 + coding-agent 코드 기준입니다. 또한 protocol/server/client(CBOR 프레이밍)는 CLI도 서비스 구현도 없는 실험 표면입니다.

SDK 쪽의 철학은 정반대입니다. 이 저장소의 패리티 문서는 Claude Code의 551개 기능 중 313개가 SDK에서 "이미 제공(provided)"이라고 채점합니다(coverage.md:679). 즉 SDK의 가치 제안은 "Claude Code의 품질을 재구현하지 않고 상속한다"이고, 그 대가가 블랙박스입니다. Anthropic 자신의 표현으로는 gather context → take action → verify work 루프를 "컴퓨터를 준 Claude"에게 맡기는 것입니다.

§3모델·프로바이더 레이어

가장 비대칭이 큰 영역입니다. Pi의 pi-ai는 그 자체로 하나의 제품 규모이고, SDK에는 프로바이더 추상화가 존재하지 않습니다.

Pi: Provider와 API를 분리한 이중 레지스트리

Pi는 프로바이더(정체성·인증·카탈로그·디스패치)와 API 전송(와이어 프로토콜)을 분리합니다(packages/ai/README.md:232-234). 10개 전송은 openai-completions, openai-responses, azure-openai-responses, openai-codex-responses, anthropic-messages, bedrock-converse-stream, google-generative-ai, google-vertex, mistral-conversations, 그리고 Pi 자체 프로토콜 pi-messages입니다. 프로바이더↔API는 다대다라서 opencode 하나가 4개 API를 쓰고, github-copilot은 3개를 씁니다.

카탈로그는 models.dev, OpenRouter, Vercel AI Gateway 세 소스에서 3,078줄짜리 생성 스크립트가 만들며 tool-call 가능 모델만 살아남습니다(if (m.tool_call !== true) continue가 26곳). 평일 cron이 재생성·재배포하므로 숫자는 설계상 계속 움직입니다. 분포는 극단적으로 상위 편중: openrouter 333 + vercel-ai-gateway 225가 43%.

추상화가 값을 하는 곳: thinking 레벨 매핑

통일된 ThinkingLevel(minimal|low|medium|high|xhigh|max)을 각 전송에 맞게 번역하는 것이 프로바이더 추상화의 진짜 난이도입니다. Anthropic은 adaptive(output_config.effort)와 budget(budget_tokens)을 분기하고 thinking이 켜지면 temperature를 제거합니다(anthropic-messages.ts:805-823, 1037). OpenAI Responses는 reasoning:{effort, summary} + include:["reasoning.encrypted_content"]. OpenAI Completions 계열은 compat.thinkingFormat으로 11개 분기(zai, qwen, deepseek, openrouter, together, baseten…)를 가지며, 토큰 상한 필드 이름만 세 가지 철자가 있습니다(openai-completions.ts:866-963, 997-1017). Google은 Gemini 3의 thinkingLevel과 Gemini 2.x의 숫자 thinkingBudget을 모델별 테이블로 나눕니다. Mistral은 none|high로 뭉갭니다.

모델 전환을 가능케 하는 공통 프리플라이트

transform-messages.ts(:64-223)가 모든 어댑터 앞에서 실행됩니다: 텍스트 전용 모델용 이미지 다운그레이드, 모델 간 thinking→text 변환과 서명 제거, 프로바이더별 tool-call id 정규화, 에러난 assistant 턴이나 결과 없는 tool call이 있는 히스토리 복구. 세션 도중 Claude에서 GPT로, 다시 Gemini로 바꿔도 대화가 깨지지 않는 이유입니다.

캐싱·비용·재시도

  • 캐시 브레이크포인트: Anthropic은 최대 3개(시스템 프롬프트, 마지막 툴 정의, 마지막 user-role 블록 — 툴 결과가 user role이므로 그것도 포함). CacheRetention = none|short|long이 1h TTL로 매핑. OpenAI Responses는 retention none이면 prompt_cache_options:{mode:"explicit"}로 명시적 옵트아웃. Bedrock은 cachePoint + 모델 allowlist.
  • 비용: 단일 함수 calculateCost()(models.ts:878-898)가 캐시 토큰을 별도 단가로, 티어(inputTokensAbove)를 요청 전체에 적용. 1h 캐시 쓰기는 base input 2×.
  • 재시도 두 층: 전송층 retryProviderRequest는 모든 벤더 SDK를 maxRetries: 0으로 호출하고 직접 감쌉니다 — SDK의 백오프 타이머가 AbortSignal을 무시하기 때문(provider-retry.ts:97-104). 서버가 60초 넘는 retry-after를 요구하면 조용히 자지 않고 즉시 실패. 턴층 retryAssistantCall은 에러 메시지를 정규식 분류하되 과금/쿼터 deny-list를 먼저 검사.
  • 에러는 스트림 밖으로 throw되지 않음: 모든 어댑터가 stopReason: error|aborted + 터미널 error 이벤트로 수렴. 25개 프로바이더별 정규식으로 컨텍스트 오버플로를 판정하고, z.ai처럼 조용히 받아들이는 경우와 Xiaomi처럼 잘라서 length를 돌려주는 경우까지 별도 감지(overflow.ts:9-63, 144-160).

OAuth 7종과 자격증명 해소 순서

Anthropic(PKCE, loopback 53692), OpenAI Codex(PKCE 1455 또는 RFC 8628 device code, JWT에서 chatgpt_account_id 추출), GitHub Copilot(device code → Copilot 토큰 교환), Kimi, xAI, OpenRouter(영구 API 키로 교환), Radius(게이트웨이별 팩토리). 어느 모듈도 디스크에 쓰지 않고 주입된 CredentialStore로 저장하며, 코딩 에이전트는 ~/.pi/agent/auth.json(0600)으로 백업합니다. 해소 순서는 "저장된 자격증명이 프로바이더를 소유한다 — 실패한 refresh 뒤에 조용히 env로 폴백하지 않는다"(auth/resolve.ts:44-49).

SDK: 프로바이더 추상화 없음, 백엔드는 env로

Options.model은 자유 문자열이고 실제 해석은 자식 프로세스 안에서 일어납니다. 백엔드(Anthropic API / Bedrock / Vertex / Foundry / 게이트웨이)는 CLAUDE_CODE_USE_BEDROCK, ANTHROPIC_BASE_URL 같은 환경변수를 자식에게 넘겨서 고릅니다. SDK 옵션이 아닙니다. 비-Claude 모델 경로는 없습니다. 이 저장소의 패리티 문서도 서드파티 백엔드는 "모델링은 했으나 실제 대체 프로바이더로 라이브 테스트한 적 없음"(full-potential.md:54)이라고 적어 두었습니다.

인증에서 가장 중요한 두 사실:

  1. 앱이 claude.ai 로그인을 제공하는 것은 계약상 금지: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." 미리 발급된 CLAUDE_CODE_OAUTH_TOKEN을 env로 넘기는 것은 동작하며(probes/28), 그때 ANTHROPIC_API_KEY가 함께 있으면 API 키가 토큰을 가립니다.
  2. 토큰 종류가 관측 가능한 표면을 바꿉니다(probe 55, clone-roadmap.md:176-200): claude setup-token으로 만든 토큰은 user:profile 스코프가 없어 usage().rate_limits가 null이고, 인터랙티브 로그인 자격증명은 subscription_type:"max"와 rate limit 전체를 돌려줍니다. 즉 env 토큰을 export하는 관행이 오히려 기능을 줄입니다.

비용 보고는 정확합니다. SDKResultMessage.usage는 메인 루프만, modelUsage가 서브에이전트·사이드체인·컴팩션까지 포함하며 "추정치이지 청구서가 아님"이라고 JSDoc에 명시(sdk.d.ts:4770-4862). costBasis: 'list'|'managed'|'unknown'까지 그대로 전달됩니다. 대신 가격표 자체나 캐시 제어는 만질 수 없고(SYSTEM_PROMPT_DYNAMIC_BOUNDARY 센티널과 promptCacheTtl 설정 키가 유일한 레버), 재시도 횟수·백오프도 내부입니다.

미해결: 구독으로 SDK를 돌리면 누가 얼마를 내는가 (2026-09-03 기준 세 출처가 충돌)
① SDK 개요 문서: 서드파티 앱이 claude.ai 로그인을 제공하는 것 금지. ② Anthropic 헬프센터: 2026-06-15 예정이던 크레딧 분리는 보류 상태, "Claude Agent SDK, claude -p, and third-party app usage still draw from your subscription's usage limits". ③ Pi 프로바이더 문서: "Third-party harness usage draws from extra usage and is billed per token, not against Claude plan limits." ②와 ③은 과금 메커니즘에서 정면 충돌합니다. 타임라인은 2026-01 토큰 거부 → 04-04 하드 블록(OpenClaw·OpenCode) → 05-13 복원 → 06-15 직전 재보류. 이 리포트는 어느 쪽도 단정하지 않습니다.

§4에이전트 루프와 툴

Pi의 루프는 273줄짜리 함수이고 당신이 읽고 훅을 꽂을 수 있습니다. SDK의 루프는 바이너리 안에 있고 당신은 이벤트를 관찰합니다.

SDK 훅에서 프로브로만 알 수 있었던 함정들

  • SessionStart 콜백이 조용한 이유는 구조가 아니라 타이밍: 디스패치가 호스트 훅 등록보다 먼저 일어남. 일부 이벤트는 프로그램 콜백만으론 무장되지 않고 Options.settings로 매처를 등록해야 함(coverage.md:836-843).
  • bypassPermissions는 룰 엔진을 건너뛰지 않음: ask만 단락하고 deny 룰은 여전히 적용(13단 사전검사 중 11번째 rung).
  • PermissionDenied는 콜백/훅 거부에는 절대 발화하지 않음 — 분류기 거부에만.
  • Query.setPermissionMode()는 실패할 수 있음: 런타임 bypassPermissions와 지원 모델 밖의 auto는 거부되고 이전 모드 유지, 조용한 폴백 없음.
  • includeHookEvents는 프로그램 훅에서 프레임을 내지 않음(dead). 훅은 "보이지 않게 실행"됨.
  • Python SDK는 33개 중 13개 이벤트가 콜백으로 불가(SessionStart/End는 settings.json 셸 훅만), can_use_tool은 더미 PreToolUse 훅이 있어야 제어 스트림이 열림.

Pi 쪽 함정은 종류가 다릅니다: 이벤트 핸들러에서 newSession/fork/switchSession/reload를 호출하면 데드락이라 ExtensionCommandContext에서만 노출(types.ts:355-389); 같은 툴 이름은 첫 등록이 이김; 인자 변조 뒤 재검증이 없음. 전부 문서에 적혀 있고 프로세스 안이라 디버거로 볼 수 있습니다.

§6기능 풍부함 체크리스트

"내장 / 확장·패키지 / 불가"로 나눕니다. SDK의 "내장"이 훨씬 많고, Pi의 "확장"이 훨씬 많습니다. "불가" 열이 결정적입니다.

§7커스터마이즈 천장

두 벽의 높이가 다릅니다. Pi의 벽은 "포크해야 한다", SDK의 벽은 "포크할 소스가 없다"입니다.

SDK의 "선언 ≠ 도달" 문제 — 이 저장소가 배운 것

SDK를 프레임워크로 평가할 때 가장 위험한 것은 sdk.d.ts를 믿는 것입니다. 이 저장소는 그 교훈을 세 번 비싸게 샀습니다.

  • 훅 발화 수는 8 → 17 → 12 → 23 → 24 → 25로 여섯 번 재측정됐고, 두 번째 재측정에서야 "지켜보던 이벤트 목록 자체가 손으로 쓴 것이라 생각 못 한 이벤트는 부재로 측정될 수 없었다"는 것을 발견해 업스트림 디스패처 레지스트리(33개)로 모집단을 바꿨습니다.
  • Claude Code 2.1.233이 신모델에서 툴 5개를 제거했을 때 SDK 타입은 한 글자도 안 바뀌었습니다. 네 표면(Options·Query·SDKMessage·exports) 이름 diff가 세 릴리스 연속 0이었지만 본문 diff는 959줄이었습니다(drift-ritual.md:62-68).
  • 공식 문서는 훅 20개, 타입은 33개, 실제 발화 25개. 문서에 존재하지 않는 필드(outputStyle)가 실려 있기도 했습니다.
  • 제어 프로토콜은 엔진이 54종을 디스패치하고 SDK가 37종을 보낼 수 있는데, 래퍼가 응답을 소비해 버려서 initialize 응답의 ~1 KB 페이로드(명령·에이전트·모델·계정 형태)를 어떤 SDK 세션도 관측한 적이 없었습니다(coverage.md:764).

Pi에는 이 문제 범주가 존재하지 않습니다. 이벤트 36개는 pi.on() 오버로드 시그니처 그 자체이고, 발화 조건은 같은 파일에서 emit 호출을 grep하면 나옵니다.

§8세션·컨텍스트·컴팩션

토큰 추정도 대비됩니다. Pi는 토크나이저 없이 CHARS_PER_TOKEN = 4, 이미지 4800자로 잡되 "마지막으로 실제 usage를 보고한 assistant 메시지를 앵커로 삼고 그 뒤만 추정"하는 앵커+테일 방식(utils/estimate.ts:63-103)이라 값싸고 문서화되어 있습니다. SDK는 정확하지만 비쌉니다.

§10선택 가이드

Pi를 고르는 경우

  • Claude 외 모델(또는 여러 벤더 혼용, 로컬 모델, 구독 OAuth 여러 개)이 요구사항일 때. 이 조건 하나면 SDK는 탈락.
  • 툴 구현·시스템 프롬프트·컨텍스트 조립·컴팩션을 자기 것으로 만들어야 할 때 (연구, 특수 도메인 에이전트, 프롬프트 실험).
  • 결정적 테스트(faux provider)와 소스 수준 디버깅이 필요할 때.
  • 터미널 제품을 만들되 TUI를 처음부터 쓰고 싶지 않을 때.
  • 라이선스 리스크(프로프라이어터리 엔진, 과금 정책 변동)를 받아들일 수 없을 때.

Agent SDK를 고르는 경우

  • Claude로 충분하고, 권한·샌드박스·서브에이전트·MCP·컴팩션을 오늘 검증된 품질로 써야 할 때.
  • 헤드리스 서비스이고 UI는 어차피 직접 만들 때 (웹 앱, Slack 봇, CI 에이전트).
  • Bedrock/Vertex/Foundry 배포와 관리형 설정(managedSettings) 정책이 필요한 조직.
  • 세션당 1 GiB 클래스의 서브프로세스 비용과 근일 단위 릴리스 드리프트를 운영으로 흡수할 수 있을 때 (이 저장소의 drift-ritual 같은 장치가 필요).
이 저장소(CC-to-SDK)와의 관계
CC-to-SDK의 북극성은 "완전히 소유 가능하고 완전히 커스터마이즈 가능한, Claude Code 품질의 하네스"입니다. 이 문서의 언어로 옮기면 SDK의 §6 열(기능 풍부함)을 유지하면서 Pi의 §7 열(천장 없음)에 도달하는 것입니다. reforge/의 스트랭글러-피그 전략(모듈 하나씩 소유 TypeScript로 바꾸고 실제 바이너리와 차분 재생으로 채점)은 정확히 두 프레임워크 사이의 빈 자리를 겨냥합니다. Pi는 그 목적지가 어떤 모양인지 보여 주는 가장 좋은 살아 있는 참조이고 — 특히 Provider/API 이중 레지스트리, transform-messages 프리플라이트, 두 층 재시도, 트리 세션, 확장 이벤트 계약 — SDK는 출발점의 품질 기준입니다.
