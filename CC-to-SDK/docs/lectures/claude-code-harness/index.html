Chapter 0Orientation: what a “harness” even is

The picture first

The model — Claude — is a brain in a jar. It can only do one thing: read text and emit text. It cannot open files, run commands, remember yesterday, or even know what time it is.

The harness is everything wrapped around that jar to turn “text in, text out” into a working software engineer: hands (tools), eyes (file readers), a conscience (permissions), a memory (sessions + CLAUDE.md), a phone line (the API client), and a face (the terminal UI).

Fig 0.1 — the harness is the ring, not the core. Every chapter of this lecture is one satellite.

0.1 Why “harness” is the right word

Anthropic's API gives you a stateless function: messages[] → message. Claude Code's entire value is the stateful, side-effectful loop built around that function — what the industry has settled on calling the agentic harness. Concretely, the harness is responsible for five irreducible jobs:

JobQuestion it answersChapters
Context constructionWhat does the model get to see this turn?4, 5
CapabilityWhat can the model do, and how are its actions executed?6–9
ControlWhich actions are permitted, by whom, under what policy?10, 11
ContinuityWhat survives between turns, sessions, machines?13
ConveyanceHow do model, user, and services talk (UI, API, telemetry)?3, 14, 15

Everything Claude Code does — every feature in its 551-row capability inventory — slots into one of those five. The model itself is a commodity accessed over HTTPS; the harness is the product.

0.2 The specimen under the microscope

This lecture is grounded in a specific artifact: the v2.1.251 release binary (2026-08-31). It is a Bun-compiled single executable — a JavaScript application frozen into a 197 MB Mach-O binary together with its runtime, 1,792 precompiled ES-module chunks, five native addons, a vendored ripgrep, and (new in this generation) a library of embedded markdown documentation the harness feeds to itself at runtime. Chapter 1 dissects the artifact; the chapters after it dissect the machine inside.

Method
Claims here come from three evidence tiers, in order of authority: (1) the beautified bundle source (cli.pretty.js, cited by line), (2) live behavioral probes run against the harness/SDK (cited as probes), (3) the February-snapshot feature taxonomy (used as a checklist, never as truth — several of its rows are provably stale, and the deltas are called out where they matter).

Chapter 1The artifact: one binary, many programs

The picture first

What installs on your machine is a single 197 MB executable. Inside it: a JavaScript runtime (Bun), 1,792 precompiled code modules, five native macOS/Linux plugins, 157 embedded documentation files — and, astonishingly, a complete copy of ripgrep. The same file is the chat app, the search engine, the MCP server, the background daemon, and the updater, depending on how you invoke it.

Evidence base: research/01-boot-config-bundle.md (1,231 lines).

1.1 Packaging

Claude Code is a Bun standalone executable (Bun 1.4.1): a Mach-O/ELF binary whose __BUN section carries an ESM chunk graph — a 19 KB entry stub plus 1,792 chunk-*.js modules, each paired with precompiled JS bytecode (why the binary shrank 325→197 MB while gaining modules). 1.2 Boot: eighteen fast paths before the CLI parser exists

The entry stub hand-parses argv before loading commander, dispatching whole sub-programs: --claude-in-chrome-mcp, --chrome-native-host, --computer-use-mcp, --daemon-worker, --bg-pty-host, --bg-spare (pre-warmed spares!), remote-control, daemon, background verbs (attach/logs/stop/respawn/rm, --bg), the FleetView agents view, self-hosted-runner, a tmux-worktree exec path, and the deep-link handler (with an argument-injection guard that rejects anything after --handle-uri <uri>). Even on the normal path, commander skips registering the entire ~19-subcommand tree unless a positional or --help is present — a deliberate boot-latency optimization (:748552). Keystrokes typed during boot are captured so they aren't lost, and MDM + keychain reads start in parallel before main is even imported.

Boot then runs an ordered, checkpointed pipeline (~50 named spans from cli_entry to after_processUserInput): config load → remote/managed settings → credentials → GrowthBook → migrations → trust → sandbox init → MCP → first prompt. Non-interactive mode triggers on -p, --sdk-url, or simply stdout not being a TTY — piping output alone makes it headless, which is why the trust dialog warns about it.

1.3 The command surface

19 top-level subcommands (gateway, auth, project, mcp, plugin, setup-token, agents, ultrareview, auto-mode, remote-control, doctor, sandbox, update, install, import, import-conversations, self-hosted-runner, daemon, plus the background verbs), and 113 flags on the main command, 43 of them hidden — the hidden set (--managed-settings, --resume-session-at, --task-budget, --teammate-mode, --agent-id/-name/-color/-type, --workload…) is effectively the SDK's private ABI. Notable dead commands: claude config and claude migrate-installer no longer exist in 2.1.251.

Boot postures worth knowing: --bare (sets CLAUDE_CODE_SIMPLE=1 — minimal mode, no hooks/plugins/CLAUDE.md, prompt collapses to CWD:/Date:), --safe-mode (all customizations disabled, for debugging broken configs), and --restricted (removes code-execution tools + WebFetch and ignores user/project/local settings entirely).

1.4 Versions and self-update

Native installs live under ~/.local/share/claude/versions/<v> with staging in ~/.cache/claude/staging and locks in ~/.local/state/claude/locks; ~/.local/bin/claude is a bare symlink into the versions dir, swapped atomically (symlink-to-tmp + rename), and the installer refuses to overwrite a launcher it didn't create. Updates: poll https://downloads.claude.ai/claude-code-releases/<channel> every 30 min → fetch manifest → SHA-256-verified zstd download → staged rename with EBUSY retries → “Update installed · Restart to apply”. Enterprise policy can pin versions both ways (requiredMinimumVersion/requiredMaximumVersion block startup). Channels are stable/latest (the schema's rc is rejected by the installer and relabeled “slow” in the UI — a genuine internal inconsistency).

Chapter 2Configuration: five tiers, one truth

The picture first

Every knob has five places it can be set, and they stack in a fixed order: user < project < local < flag < policy. Your IT department's tier (policy) always wins, and some of its keys can only tighten, never loosen. Alongside the settings files live two other control planes: ~1,000 typed environment variables, and ~355 server-side feature flags that can reshape the product between releases.

2.2 Trust

Workspace trust is per-directory in ~/.claude.json (projects[<dir>].hasTrustDialogAccepted) with an ancestor walk up to the git root — trusting a repo trusts its subdirectories (:311176). CLAUDE_CODE_SANDBOXED short-circuits it. Untrusted workspaces get their project settings ignored with an explanatory warning.

2.3 Environment variables: a typed registry

Env vars aren't read ad-hoc: a registry declares 971 variables across 8 namespaces (auth, providers/base-URLs, model selection, feature toggles, HTTP/transport, OS/terminal, telemetry, session/config) with zod-style coercions (bool = {1,true,yes,on}, triBool, clamped ints, enums) and per-variable memoization (:770014). Scrub-sets govern what crosses process boundaries: secrets (ANTHROPIC_API_KEY, CLAUDE_CODE_OAUTH_TOKEN, AWS keys…) are stripped from sandboxes; background workers strip everything starting with CLAUDE_ except a three-item allowlist plus OTEL_*.

2.4 Feature flags: GrowthBook, not Statsig

Statsig is gone — only the legacy ~/.claude/statsig directory name survives in cleanup sweeps. Flags are GrowthBook: ~355 tengu_<codename> flags with compiled-in defaults (220 default-false, 96 default-true, 39 valued), cached in ~/.claude.json under cachedGrowthBookFeatures, refreshed every 360 minutes with jitter. The accessor names encode their staleness contract honestly: getFeatureValue_CACHED_MAY_BE_STALE, _SESSION_PINNED (first read memoized so a mid-session refresh can't flip behavior), _BLOCKS_ON_INIT. Offline degrades to the per-call defaults.

The universal override pattern
resolve = envVar || bundleOptIn || serverPerConversationOverride || growthbookFlag(name, false)
Every CLAUDE_CODE_<TWO_WORD_CODENAME> env var is a local force-on for the identically-named tengu_<codename> flag (:651299). If you see CLAUDE_CODE_CARVED_SLATE in the wild, it's someone turning on the tengu_carved_slate experiment locally. For a replica this means: the flag layer is part of the product's configuration surface, not just telemetry plumbing.

Chapter 3The engine: the agentic loop, turn by turn

The picture first

The engine is one loop: send the conversation to the model → stream its reply → the moment the reply asks for a tool, start running it → feed results back → repeat. Everything else in this chapter is what makes that loop industrial-grade: it starts tools before the model finishes talking, it lets you steer mid-turn without breaking anything, and it self-heals from a dozen failure classes without bothering you.

Evidence base: research/02-query-engine-turns.md. The whole engine lives in one chunk spanning cli.pretty.js:411873–520034.

3.1 One generator, one state object, two loops

The engine is a single async generator — entry Kx :486327 wrapping the real loop DAt :486427 (~1,120 lines) — that serves every face of the product: the interactive REPL, -p headless mode, stream-json, the SDK transport, subagents (querySource: "agent:…"), even hook-agents. Loop state is one object Pe ({messages, toolUseContext, turnCount, transition, …}), and the real state machine is the transition.reason enum — 8 continuation reasons:

next_turn malformed_tool_use_retry max_output_tokens_recovery truncated_response_recovery thinking_only_retry stop_hook_blocking reactive_compact_retry precomputed_compact_swap

…and 19 terminal reasons (Zw :306736), of which completed is only one: blocking_limit, rapid_refill_breaker, prompt_too_long, image_error, model_error, api_error, malformed_tool_use_exhausted, aborted_streaming, aborted_tools, stop_hook_prevented, hook_stopped, tool_deferred, max_turns, background_requested, completed + 4 driver-level (budget_exhausted, structured_output_retry_exhausted, …).

Inside each turn hides a second loop (while(Ol) :486706) that can re-dispatch the same turn against a different model — refusal fallback, consent fallback, availability-chain advance — without ever advancing turnCount.

3.2 Streaming: complete-message-per-block, then retro-patch

The engine folds SSE events itself (the vendored Anthropic SDK's accumulator exists but is off the hot path, and its retries are disabled — every client is built with maxRetries: 0 :498036). The fold yields one complete assistant message per content block at each content_block_stop (:499122), then back-patches usage/stop_reason onto all of them when message_delta arrives (:499166). Tool-use inputs accumulate as plain strings (input_json_delta concat, no incremental parse); a healer at block close JSON-parses them, substituting a raw sentinel on failure (Uq :517784). Notable negatives: no fine-grained tool streaming beta anywhere — the eager-tool-start effect comes purely from per-block emission — and citations_delta is ignored by the engine fold entirely.

Liveness machinery: synthetic pings when raw bytes flow but no SSE event decodes for 10s (max 30); a 30s stall telemetry threshold; stream-idle timeouts (5-minute floor); and a non-streaming fallback — if a stream dies before any complete data, the turn is tombstoned, the tool executor rebuilt, and the request re-issued without streaming, telling the user to “check any proxy or gateway between Claude Code and your model provider” (:486980).

3.3 Tool scheduling: an uncapped executor with barriers

The live scheduler (ORe :484328) admits a tool the moment its block closes. Admission policy, verbatim logic:

canExecuteTool(isSafe) {
  let executing = tools.filter(t => t.status === "executing");
  return executing.length === 0 || (isSafe && executing.every(t => t.isConcurrencySafe));
}
  • No concurrency cap on this path. 30 concurrency-safe tool calls → 30 run at once. (The famous CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY ?? 10 lives in a second, legacy batch scheduler reached only from two replay paths — :459780.)
  • A concurrency-unsafe tool is a barrier in both directions: nothing starts while it runs, and it won't start until everything running finishes.
  • A schema-parse failure makes a tool unsafe (serializing it), not rejected.
  • Results are yielded in completion order within a safe batch — the wire normalizer later hoists all tool_result blocks to the front of the merged user message rather than pairing positionally (:517707), with a repair pass injecting [Tool result missing due to internal error] for any gap.
  • No sibling cancellation on failure. The string “Sibling tool uses failed” has zero hits in 2.1.251: a failed tool returns an is_error result and its siblings finish. Whole-batch discard happens only on fallback/abort events.

Aborts propagate through a tree of linked AbortControllers: each tool gets a child controller whose abort escalates to the parent — one tool's fatal abort tears down the turn — and on any abort the executor still drains, so every tool_use id gets exactly one result (real or synthetic). Unknown tool name? A synthetic completed result: <tool_use_error>Error: No such tool available: {name}</tool_use_error>.

3.4 Steering: the queue, the fold, and two kinds of “stop”

Typing while the model works enqueues a command into a priority queue (now/next/later, :421832). At turn start and after every tool batch, the engine folds eligible queued input into the running turn — landing alongside the next tool results, wrapped verbatim (:519795):

The user sent a new message while you were working:
<text>

This is how Claude Code surfaces messages the user sends mid-turn — within the running turn,
often alongside the next tool result, rather than as a separate conversation turn. Address the
message above as you continue this turn.

Fold rules: slash commands are never absorbed mid-turn; at most one prompt-mode command per fold; and the code refuses to drop input — every degradation path re-queues rather than discards (:487516–487525).

The load-bearing distinction
There are eight pre-allocated abort reasons (:742382), and two matter constantly: user-cancel (ESC) records [Request interrupted by user] — or …for tool use] if tools had started — plus synthetic per-tool results; whereas interrupt (a now-priority queued message arriving) aborts the API call silently — no marker, no synthetic results — because the queued message itself is the signal. Both SV() :742394 and dG() :480620 special-case it. Collapse the two and you either double-inject interruption noise during steering or lose the record on ESC.

Related chords: Ctrl+C also reaps background agents (plain ESC spares them); double-ESC opens the Rewind message selector; Enter can fire the queued backlog immediately by aborting with user-cancel. When a turn is aborted before tool results and the transcript ends on a user message, resume-repair either drops the unresolved assistant turn entirely (fabricating nothing) or splices a synthetic No response requested. assistant message so roles alternate (:453878, :517988).

3.5 Self-healing: retries, fallbacks, recoveries

Retry is harness-owned. kQ :445990 is an async generator (so it can yield countdown notices into the transcript while sleeping): 10 attempts default (env-clampable to 15; CLAUDE_CODE_RETRY_WATCHDOG swaps in 300 attempts / 5-min caps), backoff 500ms·2ⁿ⁻¹ capped 32s with +25% additive jitter, Retry-After honored as a floor. Subscription users don't retry 429s (their limit won't un-hit itself). 401 retries and invalidates the credential first.

Model fallback is two mechanisms. Server-side: the API itself can serve a different model (“pennant” blocks with reasons refusal/sticky, refusal categories cyber/bio/frontier_llm/reasoning_extraction :487843) — declined if the target isn't in the org's availableModels. Client-side: a fallback chain advanced on 404/403/5xx/3×529, with a subtle branch that collapses back onto the failed model with a fresh retry budget when the chain runs out (:487124). CLAUDE_CODE_NO_MODEL_FALLBACK pins the chain to one entry with a throwing tripwire.

Recovery nudges — synthetic isMeta user messages, each capped at 3 attempts: output-token overflow (“Resume directly — no apology, no recap… Pick up mid-thought”), mid-stream truncation, malformed tool call (“Please retry the tool call now.”), and a thinking-only response with no visible text. Context overflow has two distinct paths: a silent max_tokens shrink inside the retry loop (parsing the server's arithmetic out of the error string), and reactive compaction (Chapter 5) for Prompt is too long.

3.7 Envelopes: what leaves the engine

The engine's internal vocabulary is far richer than any consumer sees — 22 event types never reach the SDK (tombstone, command_lifecycle, set_in_progress_tool_use_ids, server_fallback…). Three serializations share the one generator (:358127): text (prints the final result), json (one object — or, with --verbose, silently an array of every message), and stream-json (NDJSON, one object per line — and it hard-requires --verbose or the process exits 1). The bundled SDK spawns the CLI with exactly --output-format stream-json --verbose --input-format stream-json.

Transcript records (the JSONL on disk) wrap each message with parentUuid/isSidechain/sessionId/version/gitBranch/cwd/userType:"external"/…; attachments (84 subtypes) render into <system-reminder> text — or, notably, into synthetic tool_use/tool_result pairs: an attached directory becomes a fake Bash ls call, an attached file a fake Read call (:518784). Untrusted content gets a hardened wrapper that escapes nested </system-reminder> closers (umn :74703) — a small but real prompt-injection defense.

Chapter 4What the model sees: prompt & context assembly

The picture first

Before every single API call, the harness assembles a briefing packet: who you are (the system prompt), where you are (environment, git status), what the user's standing orders are (CLAUDE.md), and what just changed (system-reminders). Almost none of it is one static string — it's ~35 sections chosen per model, per provider, per feature-flag, re-assembled from scratch on every request.

And here's the meta-trick of this lecture: you can verify most of this chapter against a live specimen, because any Claude Code session — including the one that wrote this — carries exactly these structures in its own context.

First, the headline correction: CLAUDE.md is not in the system prompt.   • @imports: resolved relative to the importing file, max depth 5, cycle-detected, skipped inside code fences, external-to-project imports require a one-time approval dialog (:496470–496554).
  • Limits: 4 MiB hard skip (not truncate!); ~40,000-char soft warning surfaced in /context; auto-memory truncated at 200 lines / 25,000 bytes.
  • Nested memory is lazy: touching a file (Read, @-mention, IDE open) triggers on-demand loading of CLAUDE.md/rules in directories between cwd and that file — once each, per session (:492668). .claude/rules/*.md may carry paths: frontmatter for glob-scoped rules loaded only when a matching file is touched.
  • Re-read suppression: Reading a file already in the memory block returns “This file is already in your context… Use that content instead of re-reading.” — the freshness ledger is seeded from memory files at init (:568742, :151118).
  • Gone in 2.1.251: the # memory shortcut (replaced by the auto-memory subsystem), AGENTS.md support (never read, despite an in-binary comment), and the old “malicious code” file-read reminder.

Chapter 5The context lifecycle: counting, compacting, caching, costing

The picture first

The model's context window is a whiteboard of fixed size. Every turn writes more on it. The harness runs four background disciplines around that whiteboard: an accountant (how full is it, exactly?), a janitor (when it's nearly full, photograph it, wipe it, and pin the photo in the corner — compaction), an archivist (keep the unchanged prefix cheap to re-send — prompt caching), and a cashier (price every token that crossed the wire).

Almost none of this is guesswork: the harness measures context from the API's own usage receipts, and only estimates the little tail that arrived since.

By default (gate on, :489266) the summarization request is issued as a fork of the live conversation — the entire history prefix is a prompt-cache hit, so the expensive compaction call costs little more than its output tokens (skipCacheWrite: true, maxTurns: 1).

Two more lanes: reactive and speculative

Reactive compaction (vte :488500) is the recovery path when the API itself rejects with “Prompt is too long”: it parses the reported token gap out of the error string and summarizes just enough turn-groups to close the gap (falling back to dropping 20% at a time), retrying up to 3 times, stripping images as a last resort. Precomputed compaction (YRe :488808) is speculative: when ~80% of the window is used (fraction is gate-tunable), a background summarization starts; the result is held ready — and even persisted to a sidecar file, rehydratable for 7 days — so that when the threshold finally trips, the swap is instant and everything that arrived meanwhile is appended to the preserved tail.

5.4 Microcompaction: server-negotiated tool-result eviction

Distinct from full compaction, microcompaction elides old tool results in place. The 2.1.251 mechanism is server-negotiated, not timer-based: on main-thread interactive turns the client advertises, under the context-hint-2026-04-09 beta, a body field context_hint: {enabled, target_tokens_saved} — but only if elision could free ≥ 20,000 tokens. If the server answers 422/424, that is the signal: the client clears all but the last 5 eligible tool results and retries (createContextHintController :564553).

Exactly 9 tools are eligible: Read, Bash, PowerShell, Grep, Glob, WebSearch, WebFetch, Edit, Write (:483538). Agent/MCP/Todo results are never elided. Text-only results are replaced by a pointer — <persisted-output>Tool result saved to: {path} … Use Read to view</persisted-output> — while results containing images are flatly replaced with [Old tool result content cleared] (images are never persisted). A related but separate mechanism persists any single oversized tool result (default cap 50,000 chars) to disk at write time, leaving a 2,000-char preview inline (:242565).

6.3 Deferral: schemas on demand

Deferral is an API feature, not a client trick: deferrable tools serialize with defer_loading: true under the advanced-tool-use-2025-11-20 beta, ToolSearch results are {type:"tool_reference", tool_name} content blocks, and the server expands them into a <functions> block at the point in the conversation where the reference appeared (:497157, :577848). Key mechanics:

  • All MCP tools are deferred by default; ~25 built-ins mark shouldDefer (NotebookEdit, WebFetch, WebSearch, BashOutput, cron tools, worktree tools…). Core tools and the three memory tools never defer.
  • A tool never ToolSearch'd is absent from the request entirely; once discovered, its name persists in the transcript (and across compaction via preCompactDiscoveredTools on the boundary marker) and it's sent with defer_loading: true.
  • A DeferredToolPlaceholder pseudo-tool (“Reserved placeholder that keeps deferred tool loading active; never call this tool.”) keeps the machinery armed when nothing is currently deferred (:497518).
  • ENABLE_TOOL_SEARCH=auto:N mode defers only when deferred schemas would exceed N% (default 10%) of the context window — measured by actually token-counting the schemas, memoized.
  • The model learns available names from a system-reminder listing; calling an unloaded tool fails with a schema-teaching error: “This tool's schema was not sent to the API… Load the tool first: call ToolSearch with query "select:<name>", then retry.”
  • ToolSearch's ranking: select: exact fetch; keyword scoring over tokenized names (+10 exact part, +12 for MCP), searchHint regex (+4), description (+2); +term requires a match.

6.4 Output budgets

Three nested limits govern tool results: per-result overflow-to-disk at min(maxResultSizeChars, 50000) chars (replaced by a <persisted-output> envelope with a 2,000-char preview and a file path); a per-assistant-turn aggregate budget of 200,000 chars that retroactively persists the largest results in the turn until it fits (:242737); and tool-specific caps — Read is Infinity (never persisted), Grep is a strikingly tight 20,000, most tools 100,000, MCP tools read theirs from _meta["anthropic/maxResultSizeChars"] clamped to 500,000. Results containing images are never truncated or persisted.

Chapter 7Tools II: files, search, and the web

The picture first

The file tools look boring — read, write, edit, search — but each hides a discipline: Read keeps a freshness ledger so the harness knows exactly which version of every file the model has seen; Edit refuses to touch anything the model hasn't read; and both search tools are fronts for the ripgrep hiding inside the binary itself.

7.1 Read

Caps: 2,000 lines default, 256 KiB, 25,000 tokens — and per-line character truncation is gone; over-token reads now auto-paginate with a [Truncated: PARTIAL view — …] banner instructing offset/limit paging (you saw a live one earlier in this very lecture's production). Output is cat -n format with no left-padding — literally <n>\t<content> (separator switches to : for tab-indented files under a flag). Images resize to 2000×2000/≤5MB base64 with JPEG-recompression fallbacks; PDFs over 10 pages require the pages param (max 20/request, extracted via poppler); notebooks flatten to cells-with-outputs. Empty files, offsets past EOF, and missing files each get a distinct system-reminder or error — missing files even get a “Did you mean X?” sibling search.

The readFileState ledger is the load-bearing structure: {content, timestamp: floor(mtimeMs), offset, limit, isPartialView?, seededFromContext?} per absolute path. Read/Write set it; CLAUDE.md files are pre-seeded at startup (enabling “This file is already in your context” dedup); Edit/Write stale-check against it — and a repeat Read of an unchanged file returns “Wasted call — file unchanged since your last Read” instead of content.

7.2 Write & Edit

Write enforces read-before-overwrite twice: a soft validateInput check and a hard re-check inside the write lock after opening the file (a TOCTOU guard, :471165). It auto-creates parent directories, forces LF endings (Edit, by contrast, preserves the file's detected encoding and CRLF), and verifies on-disk size after writing to catch silently-truncating network drives. Blocked writes include: subagent report files (/^(REPORT|SUMMARY|FINDINGS|ANALYSIS).*\.md$/i when an agentId is set — “Subagents should return findings as text”), secrets scanned on writes into shared memory directories, and Perforce read-only files (with advice to p4 edit, never chmod).

Edit's contract is exact-string replacement with a 13-code failure taxonomy (unique-match enforcement, stale-file, notebook redirect, 1 GiB cap…). Two details a replica always gets wrong: matching is not naive indexOf — a desanitization layer (vle :512858) finds the actual file substring modulo curly quotes/\uXXXX/whitespace and re-sanitizes the replacement to match the file's conventions; and the application reads from disk, not the ledger, so an externally-modified-but-still-matching file applies cleanly with an advisory note.

7.3 Glob & Grep: fronts for the embedded ripgrep

Glob = rg --files --null --glob P --sort=modified --no-ignore --hidden, capped at 100 results — note the defaults: .gitignore ignored and dotfiles included unless env-overridden. Grep maps its schema onto an explicit rg argv (--hidden, VCS-dir excludes, --max-columns 500 — where the old line-truncation moved — --json in content mode, always -n with client-side stripping if unwanted), default head_limit 250, permission-deny filtering applied after rg returns. Spawn envelope: 20s timeout (60s on WSL), 20 MB buffers, exit code 1 = no-matches-success. Security refusals worth studying: a bare-name PATH rg can't enforce Read deny-rules so out-of-tree searches are refused; and a symlink re-resolution race check refuses if link targets changed between permission check and execution.

7.4 The web tools

WebFetch is a pipeline: URL validation (≤2000 chars, no userinfo, dotted hostname) → 15-min 50 MB LRU cache → http→https upgrade → a domain preflight against api.anthropic.com/api/web/domain_info (skippable by enterprise setting) → GET with maxRedirects: 0 — redirects are followed only same-origin (protocol + port + no-userinfo + www.-stripped host equality, max 10 hops); cross-host redirects come back to the model as a structured “REDIRECT DETECTED” message with defensively-truncated URLs → Turndown HTML→markdown (1 MiB cap) → and finally the caller's prompt is answered by a side-call to the small/fast model whose template enforces a 125-char quote limit and no-song-lyrics rules (:696029). Raw surfaces skip summarization and wrap the page in an untrusted-content envelope instead.

WebSearch is a nested side-query, not a client HTTP call: a second API request with toolChoice: {type:"tool", name:"web_search"} and the server-side web_search_20250305 tool (max_uses: 8 per call), results converted to title/URL blocks with a mandatory “Sources:” instruction. A session-wide budget of 200 searches applies (CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION), with a graceful refusal message when exhausted.

Chapter 8Tools III: Bash, the sandbox, and background work

The picture first

“Run a shell command” sounds like one line of code. It isn't. Claude Code spawns a fresh shell every single time — then fakes continuity by replaying a snapshot of your shell environment and reading your working directory back out of a temp file. And around that shell it builds a jail: a generated macOS seatbelt profile or a Linux bubblewrap container, with all network traffic forced through a proxy it controls.

Evidence base: research/06-bash-sandbox-tasks.md (2,647 lines).

8.1 There is no persistent shell

Every Bash call spawns bash -c <preamble> && eval <command> && pwd -P >| <cwdfile>, detached into its own process group with stdin as a pipe (never a PTY). The preamble sources a shell snapshot, disables extglob, unsets a dangerous alias, and injects credential env. “Working directory persists” is an illusion implemented by reading that pwd -P file back — through seven validation checks (rejecting dot-segments, NT device paths, network paths, foreign automounts, non-absolute paths, network symlinks, non-directories) before the session cwd moves (:472487).

The shell snapshot — the cleverest thing in the Bash tool
Once per session (:472229), the harness runs your real shell, sources your .zshrc/.bashrc, and then dumps the resulting state into a flat script: every user function (filtering completion functions but keeping __double_underscore helpers), aliases, setopt/shopt/set -o flags, and a PATH pinned via a heredoc with a randomized terminator to defeat injection. Each list is capped at 1,000 entries; the file is unlinked at exit. Every later command sources it — which is why your aliases work but your export FOO=1 from the previous call doesn't. It also installs a pkill shim that refuses to kill the Claude process itself, printing “pkill: refusing to run — this pattern matches the Claude CLI process”.

Timeouts are exactly as documented: 120,000 ms default, 600,000 ms max (BASH_DEFAULT_TIMEOUT_MS / BASH_MAX_TIMEOUT_MS). Output caps at 30,000 chars (ceiling 150,000) with an in-memory 8 MB buffer that spills to a file, after which stdout/stderr interleave because they share one file descriptor. Exit codes are interpreted semantically per binary — for grep, rg, find, diff, test, exit 1 is not an error, only ≥2 is (:515092).

8.2 The sandbox

The sandbox is a vendored library — @anthropic-ai/sandbox-runtime, inlined at :680300–684760 — with a thin Claude Code manager on top. That boundary is real and worth copying: the library knows nothing about Claude.

macOS: generated seatbelt profile

A full SBPL program is generated per command and passed to sandbox-exec -p. It opens with (deny default) and allowlists precisely: process exec/fork, 14 named Mach services, POSIX shm/sem, three IOKit classes, ~55 specific sysctls. File rules are emitted in a load-bearing order (SBPL is last-match-wins): baseline allow → denies → allow-within-deny → glob re-denies → directory metadata always readable (so ls of a denied dir reports rather than errors) → unlink/create denies on every ancestor of a denied path (blocking the delete-and-recreate attack).

Linux: bubblewrap + one seccomp rule

bwrap --new-session --die-with-parent --unshare-net --unshare-pid --unshare-user --cap-drop ALL with a mount plan that bind-mounts read-only over denied paths, tmpfs's denied directories, and --ro-bind /dev/null over denied symlinks (explicitly “to prevent symlink replacement attack”). The vendored seccomp filter has exactly one job: block socket(AF_UNIX), because bwrap can't filter unix sockets by path. 32-bit x86 is refused outright because socketcall() would bypass it.

The anti-persistence core: a sandboxed command can never write your rc files, .mcp.json, .git/hooks, .git/config, or .claude/commands/agents — even inside an allowed write root (:683275). That list is the threat model in one constant.

8.3 Network egress: a proxy you own

With the network namespace unshared, there is no route off-box except an in-process HTTP+SOCKS mux proxy on loopback (:684240) that sniffs the first bytes to dispatch protocols. Inside a Linux sandbox, socat re-creates TCP localhost:3128/:1080 inside the namespace bridged to unix sockets on the host. Decision order per connection: no config → deny · denylist → deny · allowlist → allow · strict → deny · else ask the user — and the approval persists as a WebFetch(domain:…) rule.

The undocumented coupling
The sandbox's egress allowlist is merged from sandbox.network.allowedDomains AND your WebFetch(domain:…) permission rules (:687000). Approving a domain for WebFetch silently opens it for every sandboxed shell command too. Proxy denials are attributed back to the exact tool call because the proxy username encodes the command id.

Violations land in the model's context as a <sandbox_violations> block appended to stderr — sanitized first, with < and > stripped, because a violation line contains attacker-influenced path text and must not be able to open a tag.

8.4 The escape hatch and its politics

dangerouslyDisableSandbox is a real input field, gated by sandbox.allowUnsandboxedCommands. Setting it forces an ask carrying decisionReason: {type:"sandboxOverride"} — and that ask is not bypassable by bypassPermissions mode (:444637). “YOLO mode” still prompts to leave the sandbox. The reason is also stripped when forwarded across the remote-worker transport, so a remote worker can't inherit someone else's waiver. Conversely, autoAllowBashIfSandboxed (default true) makes sandboxed sessions feel prompt-free — subject to five carve-outs including env-var assignments, /dev/tcp redirects, and destructive rm patterns.

8.5 Background work

Four paths lead to backgrounding: explicit run_in_background, a 2-second Ctrl+B arming gesture, timeout expiry, and turn-abort. Notable renames: BashOutput and KillShell no longer exist — they're aliases for TaskOutput/TaskStop, and TaskOutput marks itself deprecated in favor of just Read-ing the task's output file. Completion arrives as a <task-notification> wrapped in the anti-spoofing envelope from Chapter 4. A gated Monitor tool streams one notification per stdout line (or per WebSocket message) and is the sanctioned answer to polling — the Bash prompt actively blocks long leading sleep commands and tells the model to use Monitor's until-loop instead.

Two absences worth recording: there is no banned-command list anywhere, and there is no Haiku-powered command-injection classifier for Bash any more — command safety is decided by a hand-written bash parser (mimicking tree-sitter-bash node names) plus the permission ladder in Chapter 10.

The Workflow tool runs a JavaScript orchestration script — agent(), parallel(), pipeline(), phase() — inside a hardened Node vm context with codeGeneration: {strings: false}.   • Resume is content-addressed. Cache keys are a chained SHA-256 over (prevKey, prompt, opts) that deliberately excludes label and phase — which is what makes “the longest unchanged prefix replays instantly” literally true when you edit a script mid-run.

Chapter 10Control: the permission system

The picture first

Before any tool runs, the harness asks: is this allowed? The answer comes from a fixed ladder of thirteen checks. The single most important property: deny is evaluated first, everywhere — before hooks, before modes, before allow rules, and again inside each shell sub-command. Nothing in the system can un-deny something.

New in this generation: a model sits inside the loop. “Auto mode” routes decisions that would have prompted you through a safety classifier instead — and when that classifier is unavailable, it fails closed.

Evidence base: research/08-permissions-policy.md (1,876 lines, 363 anchors).

10.1 Two layers, thirteen steps

An outer layer (hasPermissionsToUseTool :444272) handles hooks, mode shortcuts, and the classifier; it wraps an inner, strict rule ladder (Aon :444598). Abbreviated, in exact order:

 1 abort check
 2 whole-tool DENY rule          → deny
 3 content DENY rule             → deny
 4 whole-tool ASK rule           → ask   (unless sandbox auto-allow applies)
 5 tool.checkPermissions()          (per-tool logic; plan-mode MCP clamp)
 6 if that said deny               → deny
 7 content ASK rule              → ask
 8 requiresUserInteraction()        → ask
 9 ask-rule-driven reason           → ask
10 MCP org ceiling == "ask"         → ask
11 MODE SHORTCUT (bypass/plan)      → allow  — but safety checks survive it
12 whole-tool ALLOW rule          → allow
13 otherwise: passthrough upgraded to ask
Hooks are not terminal
A PreToolUse hook returning allow is re-run through the deny/ask rule check (Gx :444555) and loses to a deny rule — the log line is literally “Hook returned 'allow' for X, but deny rule overrides”. A hook allow bypasses the prompt, not the rules. Conversely a hook deny is terminal. Any replica modeling hooks as the final word gets this backwards.

decisionReason is a closed 11-member union — rule | mode | subcommandResults | permissionPromptTool | hook | asyncAgent | sandboxOverride | workingDir | safetyCheck | classifier | other — and it's load-bearing, not cosmetic: several branches key off the reason type (e.g. safety checks and sandbox overrides surviving bypassPermissions).

Tool or Tool(content), with backslash-escaped parens; Tool() and Tool(*) both degrade to bare Tool. Content semantics are per tool:

Containment is cwd + additionalDirectories — and note that Read is not free: reading inside the workspace is, reading outside prompts; symmetrically acceptEdits does not cover out-of-workspace writes.

10.3 Six modes

default · acceptEdits · plan · auto · bypassPermissions · dontAsk (plus an internal bubble). dontAsk auto-denies anything that would prompt. bypassPermissions refuses to start as root outside a deliberate sandbox and requires a one-time typed acceptance persisted to settings. Plan mode is a permission regime and a prompt regime: the pipeline blocks non-read-only tools and all writes except the plan file, while a system reminder restates the ban in prose.

Auto mode: a classifier in the loop

When the ladder says “ask” in auto mode, the request goes to a two-stage safety classifier model instead of the user — but only after hard floors force a real prompt anyway (safety-check reasons, ask rules, plan-mode floor, org ask ceilings, sandbox overrides). Two fast paths skip the classifier: an acceptEdits simulation (would this be allowed in acceptEdits with dangerous rules filtered out?) and a hardcoded read-only allowlist. Outcomes are allowed, blocked, refusedBySafeguard, transcriptTooLong (falls back to asking, suggesting /compact), and unavailable — which fails closed. Consecutive-denial counters trip back to manual approval with “N consecutive actions were blocked. Please review the transcript before continuing.” The classifier's own prompt sections (allow/soft_deny/hard_deny/environment) are user-editable in settings.

10.4 Managed policy

Four tiers stack: remote helper > MDM (macOS managed-preference plists read via plutil; Windows HKLM\SOFTWARE\Policies\ClaudeCode) > managed-settings.json > a managed-settings.d/ drop-in directory. Restrictive halves propagate downward always; permissive halves only while the matching allowManaged*Only lock is off. Headless sessions that would need a prompt deny with a carefully-worded message telling the model not to claim success:

Permission for this tool use was denied: it requires interactive approval, and permission prompts are not available in this session. The action was NOT performed. Do not claim it succeeded, and do not retry it in this session — report the limitation to the user, or suggest an alternative.

11.2 Types, timeouts, execution

Five settings-authorable types — command, prompt, agent, http, mcp_tool — plus two internal (callback for the SDK, function for plugin JS). The default timeout is 600 seconds, not 60 (:445027); only UserPromptSubmit (30s), the model-switch pair (30s) and SessionEnd (adaptive 1.5–60s) narrow it. Hooks for one event run fully parallel and unbounded, deduped by (pluginRoot, canonical-key) first.

Two operational traps
(1) Settings hooks are snapshotted at startup — editing settings.json mid-session does nothing until you open /hooks or restart. Plugin, skill, session and agent hooks are read live. (2) disableAllHooks in user settings does not disable hooks — it silently promotes the session to managed-settings-only. Only the managed-policy copy is a real off switch.

The hooks-worker.js shipped inside the binary is not the shell-hook runner (shell hooks spawn inline); it's a Bun Worker hosting plugin function hooks — plugin-authored JavaScript — over a structured-clone IPC protocol with a per-environment MessagePort for host callbacks.

11.3 The result contract

Exit 0 = success (stdout's meaning is per-event), 2 = blocking error with stderr fed to the model, anything else = non-blocking warning to the user only. JSON on stdout overrides all of it; a first {"async": true} line backgrounds the process. Across multiple hooks on one event, decisions fold along a strict monotone ladder — deny > defer > ask > allow — not first-wins. Hook feedback reaches the model exclusively as <system-reminder>-wrapped meta messages.

Newer output channels worth knowing: updatedInput (re-validated against the tool's schema; a schema failure converts the hook into a deny), updatedToolOutput, PostToolUse.classifierContext (a 2,000-char host assertion fed to the auto-mode classifier), SessionStart.reloadSkills/watchPaths, an OSC-allowlisted terminalSequence, and asyncRewake — a background hook that wakes the model when it exits 2.

Chapter 12Extension: MCP, the IDE bridge, and LSP

The picture first

MCP (Model Context Protocol) is how Claude Code talks to tools it doesn't ship: your database, your ticket tracker, your browser. The harness is an MCP client — it launches or connects to servers, converts their tools into its own tool objects, and defers every one of them behind ToolSearch so a hundred external tools cost almost no context.

Evidence base: research/10-mcp-ide-lsp.md (1,567 lines).

12.1 Two client runtimes, side by side

2.1.251 ships two complete MCP client implementations — v1 (default) and v2 — selected by MCP_SDK_GENERATION or a remote flag, with a runtime tripwire if the wrong one loads. Reading only one documents half the product. v2 introduces a “modern protocol era”: a single server/discover round-trip replacing the init handshake chain, a held subscriptions/listen stream for list-changed events, server-declared tools/list cache TTLs, and era negotiation with a pre-init probe plus legacy fallback.

12.2 Configuration and transports

Servers are declared in .mcp.json (read from every ancestor directory, deepest-wins — not just the project root), in ~/.claude.json at user/project scope, via claude mcp add (with add-json and add-from-claude-desktop), via --mcp-config, or bundled inside plugins. Project-scoped servers require approval (enableAllProjectMcpServers, enabled/disabledMcpjsonServers). Transports: stdio, SSE, streamable HTTP, and WebSocket — the last fully implemented but excluded from claude mcp add.

stdio servers inherit your whole environment
By default a stdio MCP server is spawned with the full parent environment, not a minimal allowlist — the allowlist path only runs under CLAUDE_CODE_MCP_ALLOWLIST_ENV. Named credentials are scrubbed, and CLAUDE_PROJECT_DIR, CLAUDE_CODE_SESSION_ID, CLAUDECODE=1 are injected. If you run untrusted MCP servers, this is the line to read twice.

12.3 Surfacing, deferral, and auth

Tools appear as mcp__<server>__<tool> and are all deferred behind ToolSearch unless alwaysLoad is set (config key or _meta["anthropic/alwaysLoad"]). Servers can also declare anthropic/searchHint, anthropic/maxResultSizeChars (clamped to 500,000), and anthropic/requiresUserInteraction per tool. OAuth for remote servers runs dynamic client registration + a loopback callback, and tokens live in the same macOS Keychain entry as your Claude login (file fallback ~/.claude/.credentials.json), keyed by a SHA-256 of the server's type+url+headers — so editing a server's URL orphans its tokens.

Three feature areas exist that no earlier analysis covers: MCP tasks (long-running tools/call with task-scoped input requests and auto-backgrounding); channels (role: "comms" servers pushing unsolicited inbound messages into your session, behind an org allowlist); and XAA (claude mcp xaa), a shared OIDC identity provider whose cached token lets marked servers authenticate silently.

One clean spec gap worth stating: Claude Code is not an MCP sampling client. It declares exactly {roots:{listChanged:true}, elicitation:{}} and registers no sampling/createMessage handler anywhere.

12.4 The IDE bridge

IDE integration is plain MCP over a loopback port discovered by lockfile — where the lockfile's filename is the port number. The extension supplies selection context, open-file context, diagnostics, and diff-view rendering; the harness exposes them as mcp__ide__ tools and as the attachments from Chapter 4. Running the relationship in reverse, claude mcp serve turns Claude Code itself into an MCP server: over stdio it exposes the entire live tool set, narrowing to an 8-tool allowlist only in HTTP mode.

Chapter 15The face: terminal UI and interaction modes

The picture first

Everything you actually see is a React app rendering to a grid of terminal cells. Not a metaphor: there is a real React 19 reconciler, a real flexbox layout engine, a double-buffered cell grid with damage tracking, and a diff that emits the minimum ANSI to patch the screen.

Evidence base: research/13-tui-modes.md (1,178 lines).

15.1 It is not Ink (any more)

It's a heavily-forked in-house renderer that kept Ink's host-element names (ink-box, ink-text, ink-link, ink-raw-ansi) and Yoga layout, but replaced the entire output path with a double-buffered cell grid: front/back frames, interning pools for styles, chars and hyperlinks, per-cell diff producing a patch list flushed in a single stdout.write (class B_e :376633). The fork adds scroll containers, focus management, absolute positioning, per-node repaint debugging and an accessibility channel — none of which upstream Ink has. The app is compiled through the React Compiler.

Output is wrapped in DECSET 2026 synchronized-update markers when the terminal is known to support them (a hand-maintained allowlist plus a tmux probe); kitty keyboard protocol, modifyOtherKeys=2, bracketed paste, focus events and theme-change notifications are pushed and popped explicitly. There are two renderer modes — classic scrollback and a fullscreen alt-screen mode (now the default for fresh installs and background sessions) with mouse tracking, hover, wheel scroll and copy-on-select — and the fullscreen path auto-disables for screen readers, tmux -CC, Windows-over-SSH, and after three crash strikes.

A third render strategy exists for accessibility: --ax-screen-reader switches to an append-only flat-text diff writer with cursor parking, not merely a styling flag.

15.2 Input

Keybindings are user-editable JSON (~/.claude/keybindings.json): 21 contexts, 141 actions, chord bindings like ctrl+x ctrl+e, a command:<slash> escape hatch, and seven hard-reserved keys. Vim mode is a genuine modal editor — NORMAL/INSERT/VISUAL/VISUAL LINE, operators d c y, text objects over 15 delimiter pairs, counts, f/F/t/T with ;/,, registers, . repeat, indent and case operators, and jk-style insert-mode remaps. Only ! survives as a mode prefix; the # memory prefix is gone.

The spinner draws from 186 verbs (Accomplishing … Zippy), user-extendable via a spinnerVerbs setting, on a six-glyph ramp with a moving shimmer, carrying elapsed time, an eased token counter, and thinking/tool sub-status. The statusline is a user command re-run on an interval and fed a rich JSON payload on stdin — including the full context_window, cost, prompt_cache and rate_limits objects from Chapter 5.

Voice mode ships: /voice hold|tap|off, the bundled audio-capture.node (falling back to sox rec), 16 kHz mono linear16 streamed over a WebSocket to a speech-to-text endpoint with interim transcripts and keyterm biasing. Chapter 16Synthesis: the eleven ideas, and how to rebuild them

The picture first

16.2 What surprised us most

Nine findings that contradict the widely-circulated picture of Claude Code — each anchored in the chapters above:

  1. Glob and Grep aren't in the default tool list on a normal POSIX run; the model is steered to find/grep through Bash.
  2. ultrathink is a system-reminder, not a token budget — and no think/think hard/megathink tier exists at all.
  3. Microcompaction is server-negotiated (a 422/424 rejection is the signal), not timer-driven; the old event name survives as a fossil.
  4. Tools start executing before the assistant message finishes, and the live scheduler is uncapped — the famous concurrency limit lives in a legacy path.
  5. The binary is its own ripgrep, re-executed with argv0="rg".
  6. A model sits inside the permission loop in auto mode, and fails closed when unavailable.
  7. 33 hook events, a 600-second default timeout, and hooks that can rewrite tool input, answer MCP dialogs, and wake the model.
  8. The system prompt has two whole shapes (classic vs lean) chosen per model and provider — plus sections that live in server-side config, not in the binary.
  9. Statsig and Sentry are both gone, replaced by GrowthBook and Datadog.

Three cautions the research surfaced repeatedly:

  • Percentage-of-surface is the wrong metric. You can wire every declared option and still not have the product, because the parts that matter most — the interactive shell, the process registry, background sessions — aren't in any option list. Judge end-to-end.
  • Verify premises against the live artifact, not against documentation. This entire lecture exists because a February-era feature inventory had drifted: rows that said “provided” were conditional, mechanisms described in detail no longer existed, and eighteen hook events had appeared with no row at all.
  • Some behavior isn't in the binary. Per-model prompt text, reminder copy, and flag defaults arrive from server-side configuration. A static reconstruction is necessarily incomplete for a live first-party session — which is a fact about the product's architecture, not a gap in the analysis.

16.4 Where this lecture is thin

Honest limits, so you know what to re-derive yourself. Each research report ends with its own open-questions section; the load-bearing ones across the set:

  • The Bash read-only classifier that decides whether shell calls run in parallel was not decompiled.
  • The Edit tool's desanitization matcher — the single most behavior-defining piece of Edit — was read at its call sites but not inside.
  • The renderer's cell-level diff minimization was traced at the interface, not the algorithm.
  • The semantics of server-side context_hint.target_tokens_saved, cache_control.scope: "global", and evict_on_complete are inferred from field names and guards, not from any statement.
  • Roughly a dozen flag predicates (what flips the MCP v2 rollout, what Xne() matches in the lean/classic decision) resolve to server state.
The closing thought
The model is the engine, but the harness is the car. Every chapter here is a decision someone made about how to hold a probabilistic system to account: measure rather than guess, deny before allow, circuit-break every loop, treat your own tool output as untrusted, and never lose the user's words. Those decisions — not the parameter count — are what makes the difference between a chat box and something you'd let near your repository.
