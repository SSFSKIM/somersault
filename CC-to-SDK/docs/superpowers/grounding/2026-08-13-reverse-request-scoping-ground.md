# Reverse-request scoping ground — do we need a server→client request channel?

**Date:** 2026-08-13 · **Status:** grounding only, no code changed · **Feeds:** the deferred
"reverse-request domain" named as future spec work in
`CC-to-SDK/docs/superpowers/specs/2026-08-11-agent-appserver-m3-design.md:17` and `:84`.

**Question.** Codex's v2 app-server protocol has 11 server→client reverse requests. Our app server
(`CC-to-SDK/harness/src/appserver/`) ships zero, by founding decision D1 — "decisions are state, not
reverse-RPC"
(`CC-to-SDK/docs/superpowers/specs/2026-07-28-agent-appserver-protocol-design.md:144-176`, `:410-412`).
Which of the 11 would actually require a reverse-request channel for us?

**Answer up front.** One. `item/tool/call` (dynamic tool calls) is the only one of the 11 whose
answerer is a *process bound to a connection* rather than a *person*, and it is a feature our engine
does not have. Five are covered or coverable by the existing park; five are Codex-internal. Codex's
own machinery independently converged on park-shaped behavior for the approval family — pending
requests survive disconnect and are replayed on resume — while keeping the failure modes a park
avoids.

**Citation convention.** All paths are repo-relative from the repository root. `codex-rs/…` is
Codex; `CC-to-SDK/…` is ours. Claims marked **[inference]** are reasoned from code rather than read
directly or proven by a test.

## 1. How a Codex reverse request works (the machinery)

The enum is generated by the `server_request_definitions!` macro:

- Macro definition — `codex-rs/app-server-protocol/src/protocol/common.rs:1265-1420`. It generates
  `enum ServerRequest` (`:1280`, each variant `{ request_id: RequestId, params }`),
  `enum ServerResponse` (`:1318`), and `enum ServerRequestPayload` (`:1354`) whose
  `request_with_id` (`:1359`) mints the wire request.
- The 11 variants — `codex-rs/app-server-protocol/src/protocol/common.rs:1529-1600`.
- Send path — `OutgoingMessageSender::send_request` (broadcast,
  `codex-rs/app-server/src/outgoing_message.rs:273`) and `send_request_to_connections` (targeted,
  `:287-351`). Both insert a `PendingCallbackEntry { callback: oneshot::Sender, thread_id, request }`
  (`:115-119`) into one process-global map `request_id_to_callback` (`:100`) and hand the caller a
  `oneshot::Receiver`.
- Reply path — `notify_client_response` (`:373-394`) / `notify_client_error` (`:395-412`), both via
  `take_request_callback` → `HashMap::remove_entry` (`:446-452`). **First answer wins; a second
  client answering the same id gets a `warn!("could not find callback")` and nothing else** (`:390`).
- Ids come from one process-wide `AtomicI64` (`:283-285`), and a response is not checked against the
  connection the request was addressed to (`codex-rs/app-server/src/lib.rs:1080-1086` →
  `codex-rs/app-server/src/message_processor.rs:748-753`). **Any connected client can answer any
  pending reverse request, including one addressed to a different client.**
- Resolution broadcast — `serverRequest/resolved` `{threadId, requestId}`
  (`codex-rs/app-server-protocol/src/protocol/v2/notification.rs:53-57`, wire name at
  `common.rs:1734`), emitted from the single site
  `codex-rs/app-server/src/request_processors/thread_lifecycle.rs:802-824` to *all* subscribed
  connections, fired immediately after `receiver.await` returns and before the outcome is inspected
  (`codex-rs/app-server/src/bespoke_event_handling.rs:1635, 1717, 1791, 1928, 1975`). So it fires on
  answer, on client error, and on server-side cancel alike.

Two things about that machinery matter for us, and both are notable because they are the *park*
model reappearing inside a request/response wire:

1. **Approvals are broadcast, not addressed.** `send_request` with `connection_ids = None` fans out
   to every initialized connection (`codex-rs/app-server/src/transport.rs:214-236`). Whoever answers
   first wins. That is our `decision/requested` fan-out plus `-33002 alreadySettled` — except Codex
   has no equivalent of telling the loser it lost (it just warns server-side).
2. **Pending requests are replayed to a reconnecting client.**
   `replay_requests_to_connection_for_thread` (`codex-rs/app-server/src/outgoing_message.rs:353-372`)
   re-sends every still-pending `ServerRequest` for a thread, sourced from
   `pending_requests_for_thread` (`:454-467`). Exactly one caller: the running-thread `thread/resume`
   path (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:744-747`). Integration tests
   `codex-rs/app-server/tests/suite/v2/thread_resume.rs:3655` and `:3792` assert the replayed request
   equals the original byte for byte. **That is `subscribe.ts`'s replay step
   (`CC-to-SDK/harness/src/appserver/subscribe.ts:131-132`) implemented on the other side of the
   wire.**

### The classification rule

The useful test is not "request versus state". It is **whose liveness the answer depends on**:

> A decision whose answerer is a **person** survives a disconnect, because a different person can
> answer it. A capability whose answerer is a **process** does not, because the process *is* the
> connection.

Every (A) row is a person. Every (B)-shaped row (#6, and #7–#9 in their own domains) is a process
holding something only it has: a tool implementation, a credential, a signing key, a clock. That is
the whole boundary, and it maps cleanly onto Codex's own routing: the person-answered requests
broadcast (`send_request`, `connection_ids = None`), while the process-answered ones narrow to a
specific connection — `first_attestation_capable_connection_for_thread`
(`codex-rs/app-server/src/thread_state.rs:340-358`, used at `attestation.rs:69-75`) and
`require_single_current_time_connection` (`codex-rs/app-server/src/current_time.rs:142-151`), whose
comment says it outright: *"External clocks are not interchangeable, so do not choose one silently."*

## 3. The (A) rows — what covers them, and the payload gaps

Our park surface, for reference:

- Decision kinds — `permission | question | plan`
  (`CC-to-SDK/harness/src/permissions/types.ts:33`), routed by tool name in
  `CC-to-SDK/harness/src/permissions/gate.ts:26` (`AskUserQuestion` → `question`, `ExitPlanMode` →
  `plan`, everything else → `permission`).
- Answer union — `CC-to-SDK/harness/src/appserver/schema/decisions.ts:12-23`; kind→answer validation
  in `ANSWER_KINDS` (`CC-to-SDK/harness/src/appserver/broker.ts:12-16`).
- Park registry — `ThreadDecisions` over `PendingDecisions` with `expireAfterMs: "never"`
  (`CC-to-SDK/harness/src/appserver/broker.ts:47-48`); `decision/requested` notification,
  `decision/respond` method, `decision/resolved` broadcast, replay on subscribe
  (`CC-to-SDK/harness/src/appserver/subscribe.ts:131-132`).

### 3.1 Command execution (#1), file change (#2), permissions escalation (#5) → `permission`

Decision mapping, both directions:

| Codex decision | Ours |
|---|---|
| `accept` | `allow_once` (optionally with `updatedInput`) |
| `acceptForSession` | `allow_with_updates` echoing the engine's own suggestion with `destination: "session"` (probe 78; `CC-to-SDK/harness/src/permissions/types.ts:17-21`), or legacy `allow_always` |
| `decline` | `deny { feedback }` |
| `cancel` | `deny` + `abortTurn: true` (`CC-to-SDK/harness/src/appserver/schema/decisions.ts:27`) — this is exactly Codex's `decline`-vs-`cancel` split, adopted as pattern 5 in the spec (`…protocol-design.md:74`) |
| `grantRoot` (#2) | `allow_with_updates` carrying an `addDirectories` `PermissionUpdate` — the SDK's own vocabulary |
| `scope: turn \| session` (#5) | `allow_once` vs. `allow_with_updates` with a session destination |

**Recorded payload gap, not a channel gap.** Codex's `acceptWithExecpolicyAmendment` and
`applyNetworkPolicyAmendment` arms (`v2/item.rs:60-79`) carry sandbox-policy objects
(`ExecPolicyAmendment`, `NetworkPolicyAmendment`) that have no counterpart in the Claude Agent SDK.
Our nearest equivalent is the escalation path probe 80 verified — the model re-issues a Bash call
with `dangerouslyDisableSandbox: true`, `canUseTool` is consulted, and the flag is visible in the
input, so a broker can allow or predictively inject it via `updatedInput`
(`CC-to-SDK/probes/probes/80-sandbox-escalation-broker.ts:5-12`). That is a *different and coarser*
escalation vocabulary reaching the same park. Nothing about it wants a reverse request.

### 3.2 Request user input (#3) → `question`

`ToolRequestUserInputParams.questions[]` is `AskUserQuestion` with different field names.
Ours: `question_answer { answers: Record<string, string>, response?: string }`
(`schema/decisions.ts:19`), where `response` is the free-text "Other" branch (probe 65E).

Two recorded deltas:

- **Multi-select.** Codex's answer is `Record<questionId, { answers: string[] }>`
  (`v2/item.rs:1675-1685`) — one question can take several selections. Ours is one string per
  question. Widening is a schema change to `decisionOutcomeParams`, not a channel.
- **`isBlocking: false`.** Codex lets a client be told "you need not wait indefinitely"
  (`codex-rs/app-server/README.md:1621`). A park has no non-blocking mode: it parks or it does not.
  **[inference]** Nothing in the SDK's `AskUserQuestion` consult carries a non-blocking hint, so
  there is nothing on our side to project — but if it appears, it is a field on the park, not a
  channel.

### 3.3 MCP elicitation (#4) → A-extend, a fourth decision kind

This is the only row where "already covered" would be a false claim, and the only one worth building.

What exists on our side today:

- The SDK exposes `onElicitation` as an `Options` callback; we model it as a config passthrough —
  `CC-to-SDK/harness/src/config/types.ts:138`, applied at
  `CC-to-SDK/harness/src/config/resolveOptions.ts:95`.
- It is live-verified, not assumed: probe 43b drove a full round trip against a stdio MCP server —
  server `elicitInput` → `Elicitation` hook → `onElicitation` accept + content → `ElicitationResult`
  hook → content back to the tool (`CC-to-SDK/probes/probes/43b-elicitation-stdio.ts:1-4, 44-50`;
  recorded at `CC-to-SDK/docs/parity/full-potential.md:80`). SDK-type in-process servers **cannot**
  elicit ("Client does not support form elicitation"); unhandled elicitations auto-decline.
- The app server does **not** wire it. `CC-to-SDK/harness/src/appserver/mcp.ts` is the topology
  quintet only; no elicitation surface exists on the wire.

Why it is A-extend and not B: the answer is a form filled by a human. It blocks an MCP tool call, it
can wait, and any attached human can supply it. Codex's own response union
(`accept | decline | cancel` + `content`, `v2/mcp.rs:737-748`) is answer-shaped, not
execution-shaped. Parking it is strictly better than Codex's handling — see §5, where Codex
auto-declines elicitations for a whole client version line because that client could not render
them (`codex-rs/app-server/src/request_processors/thread_processor.rs:4616-4625`).

The build, if we take it: a `elicitation` decision kind, an outcome
`{ kind: "elicitation_respond", action: "accept"|"decline"|"cancel", content?: unknown }`, a row in
`ANSWER_KINDS`, and the `onElicitation` callback wired to `ThreadDecisions.broker()` the way
`canUseTool` already is. Zero new wire *shapes* — `decision/requested`, `decision/respond`,
`decision/resolved` carry it unchanged.

## 4. The one (B): `item/tool/call` — why parking fails

**What it is.** A client passes `dynamicTools` in `thread/start`
(`codex-rs/app-server/README.md:293`, `:1703-1714`): named functions, optionally namespaced,
optionally `deferLoading`. When the model calls one, the server sends `item/tool/call` to the client
and waits for `{contentItems, success}` — which becomes the tool result the model reads. The client
is the tool runtime.

**Could it ride the park mechanically?** Yes. A park is `state + a respond method`, and
`{contentItems, success}` is a fine answer payload. Nothing in `PendingDecisions` would break. That
is precisely why the question needs the liveness test rather than a shape test.

**What breaks, concretely, if we park it:**

1. **The park outlives the only party that can answer it.** `expireAfterMs: "never"`
   (`CC-to-SDK/harness/src/appserver/broker.ts:48`) is correct for a human decision and wrong here.
   The tool body lives in the client's process. When that client disconnects, the entry stays parked
   forever, the turn stays blocked inside the tool call, and `status.waitingOn` reports a thread
   waiting on an answer that has become physically impossible. A permission park waits for *a*
   human; this would wait for *a specific dead process*.
2. **Any client can answer, and here that is a correctness hole, not a feature.** Our
   `decision/respond` validates kind and stamps `by`
   (`CC-to-SDK/harness/src/appserver/broker.ts:118-127`), but does not — and by D1's design should
   not — require the responder to be the party that registered anything. First-answer-wins is the
   point. For a permission decision that is right: two humans, either may approve. For a dynamic
   tool it means a second client can fabricate a tool result the model consumes as fact. Codex has
   the identical hole (`codex-rs/app-server/src/lib.rs:1080-1086`: responses are not checked against
   the addressed connection) — but Codex's hole is a bug in a request channel, whereas ours would be
   the documented semantics of the park.
3. **There is no honest auto-settle.** Every path that force-settles a park uses
   `{kind: "deny", by: "system"}` and the gate composes a human-voiced message
   (`CC-to-SDK/harness/src/permissions/gate.ts:40-44`). For a tool call there is no denial to give —
   `{success: false}` would report an execution failure that never executed. `ThreadDecisions.reset()`
   and `teardown()` would each be manufacturing a tool result. The comment on `discard()`
   (`CC-to-SDK/harness/src/appserver/broker.ts:129-142`) already articulates exactly this objection
   for fleet views: announcing a
   settlement nobody made is what an audit-logging client records as fact.
4. **Registration has no home in the park model.** The tool set is declared per connection at
   thread start. A park registry keyed by `threadId` has no place to record "these tools exist only
   while connection *c* is alive", nor to tear the registration down when *c* drops.

**Whether we need it at all.** Not today. There is no client-provided-tool feature in our app server
— the closest surfaces run the *other* direction: `fs/read`, `fs/search` and `thread/shellCommand`
are client→server methods the server executes on this machine
(`CC-to-SDK/harness/src/appserver/workspace.ts:1-12`). The SDK's analogue of a caller-owned tool is
an in-process `type: "sdk"` MCP server, which a remote client cannot supply over a socket. So:
`item/tool/call` is the one row that would genuinely require a new channel — for a feature we have
not chosen to build.

## 5. The (C) rows that are B-shaped — and what they teach

#7 auth-token refresh, #8 attestation, #9 external clock are not applicable to us, but they are the
purest examples of the liveness rule and are worth keeping on the record because a future need in
those *domains* would land in (B), not (A):

- **#9 external clock** is the sharpest. It is the only one that will not accept a substitute
  answerer: `require_single_current_time_connection` errors unless exactly one client is subscribed,
  with the reason in the code — *"External clocks are not interchangeable, so do not choose one
  silently"* (`codex-rs/app-server/src/current_time.rs:142-151`). Before sending, it waits up to 10 s
  for a subscriber to exist at all (`:90-101`), and a failed/canceled/timed-out/malformed response
  **stops the turn before the model request is sent** (`codex-rs/app-server/README.md:1633`).
- **#8 attestation** degrades instead of failing: no capable connection → return `None` and omit the
  header (`codex-rs/app-server/src/attestation.rs:69-71`; README `:1629`: *"If no initialized client
  opted into attestation, app-server omits `x-oai-attestation` for that upstream request."*).
- **#7 auth refresh** broadcasts and relies on its 10 s timeout
  (`codex-rs/app-server/src/external_auth.rs:42-63`).

All three are gated at `initialize` by client-declared capability —
`InitializeCapabilities { experimentalApi, requestAttestation, mcpServerOpenaiFormElicitation, optOutNotificationMethods }`
(`codex-rs/app-server-protocol/src/protocol/v1.rs:44-60`), read at
`codex-rs/app-server/src/request_processors/initialize_processor.rs:72`. **A capability query is
per-connection by construction: there is nothing to park, because the question is "what can *you*
do".** Our `initialize` (`CC-to-SDK/harness/src/appserver/schema/core.ts:5-12`) carries
`clientInfo`, `authorization`, `watchThreads`, `optOutNotificationMethods` — no capability
negotiation, and none of the 11 gives us a reason to add one.

## 6. No client connected: what Codex actually does

This is the direct evidence about whether the pattern degrades. It is worse than expected.

### 6.1 Timeouts exist for exactly three of the eleven — none of them an approval

| Request | Timeout | Site |
|---|---|---|
| `attestation/generate` | **100 ms** | `codex-rs/app-server/src/attestation.rs:19`, applied `:82` |
| `account/chatgptAuthTokens/refresh` | **10 s** | `codex-rs/app-server/src/external_auth.rs:18`, applied `:46` |
| `currentTime/read` | **10 s** | `codex-rs/app-server/src/current_time.rs:25`, applied `:91` and `:117` |

Each calls `outgoing.cancel_request(&request_id)` on expiry and returns a typed failure.

Every thread-scoped request — all five person-answered ones plus the dynamic tool call — does a bare
`let response = receiver.await;` with no timer:
`codex-rs/app-server/src/bespoke_event_handling.rs:1927` (file change), `:1974` (command exec),
`:1634` (user input), `:1716` (elicitation), `:1790` (permissions), and
`codex-rs/app-server/src/dynamic_tools.rs:23`. `ToolRequestUserInputParams.autoResolutionMs` is a
client-side UI hint the server forwards and never keys a timer off; the field is marked deprecated
(`codex-rs/app-server-protocol/src/protocol/v2/item.rs:1637-1640`).

### 6.2 Cancellation is coarse: turn-bounded, not request-bounded

`abort_pending_server_requests` (`codex-rs/app-server/src/outgoing_message.rs:177-192`) drains every
pending request for the thread and sends each oneshot an error tagged
`{"reason": "turnTransition"}` (`codex-rs/app-server/src/server_request_error.rs:3-12`). It runs on
`TurnStarted` (`bespoke_event_handling.rs:158`), `TurnComplete` (`:188`), and `TurnAborted`
(`:1094`), with the comment: *"All per-thread requests are bound to a turn, so abort them."* Every
handler recognises the tag and returns without submitting anything to core
(`:1938`, `:2027`, `:1639`, `dynamic_tools.rs:26`); elicitation maps it to `Cancel` (`:1748-1754`).

`DynamicToolCall` cannot be cancelled individually at all — its `pending_request_id` is discarded at
the call site (`bespoke_event_handling.rs:1006`, `let (_pending_request_id, rx)`).

### 6.3 A client that disappears mid-approval hangs the turn

Trace, all observed:

1. Delivery to a dead connection is a silent no-op —
   `codex-rs/app-server/src/transport.rs:142-145` warns and returns `false`; the caller discards it
   (`:210-212`).
2. `OutgoingMessageSender::connection_closed` (`outgoing_message.rs:234-237`) clears only inbound
   `request_contexts`. **It never touches `request_id_to_callback`.**
3. The idle-unload path that *would* free it — *"thread {thread_id} has no subscribers and is idle;
   shutting down"* (`codex-rs/app-server/src/request_processors/thread_lifecycle.rs:411`, then
   `cancel_requests_for_thread(thread_id, None)` at `:416`) — is gated by `unloading_target()`
   (`:56-63`), which returns `None` unless the thread is inactive. A pending approval marks it
   active: `pending_permission_requests > 0` → `ThreadActiveFlag::WaitingOnApproval` →
   `ThreadStatus::Active` (`codex-rs/app-server/src/thread_status.rs:434-445`). The unload delay is
   30 minutes anyway (`thread_lifecycle.rs:5`).

**[inference, from the chain above — no test covers it]** An approval whose client disconnects and
never returns hangs indefinitely: no timeout, no unload, no cancel. The turn stays blocked. It
resolves only if a client reconnects and answers, or something else drives a turn transition.

### 6.4 Zero connections is worse than a disconnect

`ThreadScopedOutgoingMessageSender::send_server_notification` early-returns when `connection_ids` is
empty (`codex-rs/app-server/src/outgoing_message.rs:165-167`). `send_request` has **no such guard**
(`:134-145`). With zero subscribers, `send_request_to_connections(Some(&[]), …)` iterates an empty
slice, `send_result` is `Ok(())` (`:338-341`), and the entry is inserted and left pending forever —
serialized to nobody, with no error anywhere. This is the case D1 was written against, and it is
unhandled upstream.

### 6.5 When the callback *is* dropped, the answer becomes a denial

Where cancellation does fire with `error: None` (thread teardown —
`thread_lifecycle.rs:412-416`, `codex-rs/app-server/src/request_processors/thread_processor.rs:873-877`),
the oneshot sender drops and the receiver's `Err(RecvError)` arm runs:

- command exec → `ReviewDecision::denied("approval request failed")` +
  `CommandExecutionStatus::Failed` (`bespoke_event_handling.rs:2035-2039`)
- patch approval → `ReviewDecision::denied("approval request failed")` (`:1943-1946`)
- elicitation → `McpServerElicitationAction::Decline` (`:1762-1768`)
- dynamic tool → `fallback_response("dynamic tool request failed")` (`dynamic_tools.rs:31-34`)

So Codex's failure semantics are: hang while a human might still arrive; deny when the thread dies.
Our equivalents are the same denial, but deliberate and announced —
`ThreadDecisions.reset()`/`teardown()` emit `decision/resolved {by: "system", answer: {kind: "deny"}}`
per settled entry, and `discard()` exists precisely so a *detach* announces nothing
(`CC-to-SDK/harness/src/appserver/broker.ts:139-178`).

### 6.6 A per-client-identity behavior override

`xcode_26_4_mcp_elicitations_auto_deny`
(`codex-rs/app-server/src/request_processors/thread_processor.rs:4616-4625`) auto-denies **every**
MCP elicitation for `clientName == "Xcode"` at version `26.4`, because that client shipped before
elicitation requests were client-visible. The flag is threaded into core and flips engine behavior
(`codex-rs/core/src/session/mod.rs:1579-1589`). That is the reverse-request pattern's tax made
literal: because the engine's behavior depends on what the connected client can render, a client
that cannot render becomes a silent policy change on the agent.

## 7. What this says about D1

D1 was chosen for detach-first survival. The evidence above supports it on a second, unanticipated
axis: **Codex's own machinery converges toward the park for the person-answered family, and the
places it has not converged are its rough edges.**

- Converged: broadcast fan-out with first-answer-wins (§1.1), a resolution notification to all
  subscribers (`serverRequest/resolved` ≡ our `decision/resolved`), and byte-identical replay of
  pending requests to a reconnecting client (§1.2, tests at
  `codex-rs/app-server/tests/suite/v2/thread_resume.rs:3655`).
- Not converged, and each is a defect a park does not have: no zero-connection guard (§6.4),
  indefinite hang on a vanished client (§6.3), turn-boundary cancellation that silently drops a
  human's pending decision (§6.2), no way to tell a losing responder it lost (§1), and no
  connection-affinity check on responses (§1).

The honest reading: we do not need a reverse-request channel to reach parity on the domain. We need
one *decision kind* (elicitation), some *payload* widening on two existing kinds, and — only if we
ever choose to let clients supply tools — one genuine channel.

## 8. Open questions

1. **Elicitation: park or decline?** Wiring `onElicitation` to the broker gives a browser client a
   real form to fill. Not wiring it keeps the current behavior (unhandled → auto-decline), which is
   what our app-server-spawned threads do today. Worth building only if a client will render forms;
   otherwise the gap is a documented non-goal. *(Needs a product call, not more research.)*
2. **Multi-select answers.** Widening `question_answer.answers` from `Record<string, string>` to
   `Record<string, string[]>` is a breaking wire change on `decision/respond`. Is the SDK's
   `AskUserQuestion` even capable of multi-select? Unverified — no probe covers it.
3. **Does the SDK ever consult for something with no human answer?** The one row that forced (B) was
   a Codex feature we lack. **[inference]** I found no SDK callback whose answerer is a process
   bound to a client connection. `spawnClaudeCodeProcess`, `onUserDialog` and `canUseTool` are all
   in-process host callbacks, not remote-client capabilities. Worth a deliberate sweep of the 63
   `Options` fields before concluding the channel is unneeded forever.
4. **Client-provided tools: is it wanted?** If a browser console should expose page-local
   capabilities to the agent, #6 becomes real and needs a channel with connection affinity and
   registration teardown. Nothing in M1–M3 asked for it.
5. **Should `decision/respond` grow a responder constraint?** Not needed for any (A) row, but if
   a channel is ever added the two models must not share a validation path — first-answer-wins and
   addressed-answer-only are contradictory defaults.
6. **`isBlocking` and non-blocking asks.** Unverified whether the SDK surfaces any non-blocking
   consult. If it does, the park needs an auto-settle policy per entry rather than the current
   thread-wide `unattended: park | deny`.
