# Codex Adversarial Review

Target: working tree diff
Verdict: needs-attention

No-ship: D6/D7 target sequencing anchors instead of rendered blocks, D9 conflates expansion state with painted cells, and T-MENU contains unsupported data assumptions, behavior regressions, and a false canon tab order.

Findings:
- [high] Separator insertion over raw anchors creates phantom and duplicate gaps (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-space.md:15-38)
  `Anchored` entries are not equivalent to visible blocks. `projectMessageEntry` filters `tool_use`/`tool_result` content (`toolRenderer.tsx:846-881`), but `buildAnchoredEntries` retains those empty records (`:1423-1441`) and `projectAll` later adds the visible completed-tool anchor (`:1605-1611`). Prepending at `weaveStandaloneHooksFlat` therefore emits blanks for invisible carriers and another for the actual tool. Coalesced teammate and hidden-content anchors have the same failure mode. A stability-only ID test also misses collisions that `publishedIds` would silently deduplicate.
  Recommendation: Define separators over non-empty realized render units, not raw anchors. Give each separator a unique durable boundary ID and test empty tool carriers, hidden notices/thinking, suppressed tools, coalesced entries, pairwise ID uniqueness, and real Static commit/reprojection transitions.
- [high] The two new chrome rows invalidate hard dock budgets (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-space.md:40-57)
  The current measured maximum dock is hard-coded as 14 rows, including spinner=1 and composer=3 (`liveWindow.ts:38-56`). Adding `marginTop:1` to both raises the maximum to 16, but the plan names neither `liveWindow.ts` nor `dockDialogRows`, which also charges the live-turn slot as one row (`ChatApp.tsx:1730-1737`). Leaving 14 consumes the two-row safety slack and can trigger Ink's `outputHeight >= rows` full-transcript clear/replay path on spinner ticks. The palette condition is also not buildable from the named files because its authoritative state lives in `ChatComposer.tsx`, not `composerFrame.tsx`.
  Recommendation: Explicitly remeasure and update every production budget, including `MAIN_DOCK_ROWS` and `dockDialogRows`; wire palette state through `ChatComposer`; add maximum-dock tall-write tests at short/normal terminal heights for spinner, retry, compaction, and palette-open states.
- [high] Status-family rerouting removes existing correctness and information (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-menu.md:57-68)
  The existing dialog loaders are not equivalent to the command arms. `/status` performs a fresh context measurement (`useChat.ts:2254-2268`), while `fetchSettingsStatus` explicitly uses possibly absent or stale `ctxPct` (`:3078-3084`). `/cost` currently renders cost, duration, code-change, and per-model usage details (`commands.ts:314-349`), whereas the Usage tab only renders plan-rate-limit bars (`usageFormat.ts:49-54`). `/stats` also emits an in-flight staleness warning that its tab loader omits. The planned switch-arm replacement would silently regress all three.
  Recommendation: Make opening source/tab explicit and preserve each command's semantics in its dialog loader: fresh context for Status, verified cost content for `/cost`, and the in-flight disclaimer for Stats. Add behavior-equivalence tests before removing the text arms.
- [high] The MCP drill-down depends on a nonexistent tool inventory (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-menu.md:70-85)
  `ChatSession` exposes no global session tool inventory—only `capabilities()` and `mcpServerStatus()` (`session/chatSession.ts:16-29`). The SDK already returns raw per-server tools and descriptions in `McpServerStatus.tools` (`sdk.d.ts:1141-1151`); those names are not a flattened `mcp__<server>__...` catalog. Following the plan literally leaves the tools/detail views empty or forces unnecessary public and wire expansion. The proposed reused fixtures only cover empty and `{name,status}` rows, so this can still test green.
  Recommendation: Define a typed normalization of `mcpServerStatus()` and derive drill-downs from each row's `config`, `scope`, and `tools`. Test rich local and remote payloads, raw names/descriptions, absent or malformed fields, and failed/needs-auth/pending/disabled states.
- [high] Permissions scope follows a false canon order and cannot meet its own acceptance (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-menu.md:42-55)
  The research/spec claim `Workspace · Allow · Ask · Deny · Recently denied · Auto mode`, but canon 2.1.251 constructs `Recently denied · Allow · Ask · Deny · Auto mode · Workspace` at `cli.pretty.js:829953-829960`, matching the current first five tabs. The planned reorder is therefore a regression. Separately, Task 2 permits a static empty Auto tab while A3 requires it to be functional; the current model only supports allow/ask/deny rules and no task defines Auto-mode builtins, environment data, or mutations.
  Recommendation: Correct the evidence and insert Auto mode before Workspace. Either design and stage its real data/mutation contract or explicitly narrow acceptance to a display-only partial tab; pin exact tab order, keyboard cycling, and narrow-pane geometry.
- [high] The parallel merge topology omits shared ChatApp geometry (CC-to-SDK/docs/superpowers/specs/2026-08-31-bl10-menus-click-spacing-design.md:111-117)
  The spec calls T-MENU and T-SPACE disjoint, but T-MENU adds an MCP `overlayChain` arm in `ChatApp.tsx` and T-SPACE changes the same dock's spinner geometry. A rows-dependent MCP browser must also join `paneOwned`; otherwise transcript, task panel, and spinner remain mounted beside it, re-entering the documented tall-frame/scrollback-repaint failure class. The T-MENU plan neither requires this partition update nor tests it, and a parallel T-SPACE branch cannot validate the combined geometry.
  Recommendation: Serialize the MCP stage after T-SPACE or declare `ChatApp.tsx` a mandatory reconciliation seam. Add MCP state to `paneOwned`, pass authoritative rows/columns, and run combined short-terminal and maximum-dock integration tests.
- [medium] Expanded state is not a valid proxy for painted hit cells (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-click.md:18-40)
  Task 1 widens every expanded row, while Task 2 says spacing separators must remain outside the band. Existing absorbed-thinking spacing is already a blank item carrying both `expanded:true` and `foldAnchor` (`toolRenderer.tsx:1061-1071`), so D9 would make that visually unbanded margin collapse the cluster. Ordinary expanded headers have the same mismatch: headers are tagged expanded, but only result bodies currently receive `withExpandedMarker` (`:561-587`). Separate hit-width and SGR tests will not catch this cell-level divergence.
  Recommendation: Introduce one explicit row-level band-cell marker and derive both full-width paint and hit width from it. Separators must carry neither the marker nor a click target. Test header, body, padding, and separator cells together on the same rendered frame.
- [medium] Live assistant streaming bypasses the spacing invariant (CC-to-SDK/docs/superpowers/plans/2026-08-31-bl10-t-space.md:19-38)
  The planned concat sites cover finalized and pending projections only. Classic mode appends raw streaming lines directly (`Transcript.tsx:27-32`), while fullscreen independently converts them through `streamingItems` (`FullscreenViewport.tsx:371`); neither traverses the anchor logic. A live assistant block therefore remains glued to its predecessor and gains its blank row only when finalized, causing a visible geometry jump despite all proposed projection tests passing.
  Recommendation: Add one stable, unbanded separator to the shared streaming representation and cover classic/fullscreen first delta, subsequent deltas without accumulating gaps, and streaming-to-finalized transition with exactly one gap.
